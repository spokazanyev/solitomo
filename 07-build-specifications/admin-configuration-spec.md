# Спецификация Админки Soliton

Дата: 2026-05-15.

SDD feature: `specs/016-admin-configuration-system`.

## Назначение

Админка Payload должна стать рабочим инструментом управления сайтом Soliton, а не только местом просмотра заявок. Через нее должны конфигурироваться данные, которые регулярно меняются или требуют участия менеджера, редактора, SEO-специалиста или администратора.

На текущем этапе в админке есть только:

- пользователи;
- заявки на КП `rfq-requests`.

Целевое состояние: админка управляет каталогом, SEO-посадочными, карточками товаров, документами, контентными блоками, заявками, аналитическими настройками и частью операционных справочников.

## Multi-Agent Operability

Админка должна проектироваться так, чтобы Codex, Claude Code или другой подключенный агент мог после диалога с владельцем сайта вносить согласованные изменения в данные сайта предсказуемо, проверяемо и безопасно.

Payload admin является не только UI для человека, но и структурированным операционным слоем для агента.

Подключенный агент должен уметь:

- найти нужный товар, категорию, страницу, документ или заявку по SKU, slug, URL, названию или внутреннему ID;
- предложить изменение в виде понятного diff;
- внести изменение как черновик или непубличную версию;
- запустить проверки качества данных, SEO, schema.org и публичного рендера;
- показать владельцу результат на preview/public URL;
- после подтверждения опубликовать изменение;
- оставить audit trail: кто инициировал изменение, что поменялось, почему и когда.

Подключенный агент не должен:

- править production-контент через неструктурированный HTML;
- публиковать изменения без проверки обязательных полей;
- открывать к индексации технические или параметрические URL;
- менять цены, юридические claims, сертификаты, реестровые утверждения или интеграционные настройки без явного подтверждения;
- хранить секреты платежей, API и интеграций как обычные текстовые поля.

## Agent Context Packet

Любой подключающийся агент должен получить единый пакет контекста проекта до внесения изменений.

Пакет должен отвечать на вопросы:

- что за сайт создается;
- какая коммерческая задача сайта;
- кто целевые покупатели;
- почему выбран стек Next.js + Payload + PostgreSQL;
- какие решения уже приняты;
- какие изменения уже выполнены;
- какие документы являются источником требований;
- какие задачи в плане следующие;
- какие команды можно запускать;
- какие коллекции, API и scripts можно использовать;
- какие действия требуют подтверждения владельца.

Обязательные источники контекста:

- `AGENTS.md` - краткие правила для всех агентов;
- `apps/web/CLAUDE.md` - точка входа для Claude Code;
- `07-build-specifications/document-register.md` - реестр документов;
- `05-implementation-roadmap/development-roadmap.md` - порядок разработки;
- `05-implementation-roadmap/sdd-step-by-step-execution-plan.md` - SDD-процесс;
- `07-build-specifications/admin-configuration-spec.md` - модель админки;
- `07-build-specifications/technical-project-foundation.md` - технический фундамент;
- `07-build-specifications/seo-technical-spec.md` - SEO/schema.org/robots/canonical;
- `07-build-specifications/product-data-spec.md` - товарные данные;
- `07-build-specifications/product-attributes-normalization-spec.md` - атрибуты и controlled values;
- `07-build-specifications/checkout-rfq-spec.md` - заявки и RFQ;
- `specs/` - текущие SDD feature specs.

Нужен отдельный machine-readable файл `agent-project-context.json` или `agent-project-context.md`, который будет кратко агрегировать:

- project summary;
- current architecture;
- current implementation status;
- next roadmap steps;

- public routes;
- admin routes;

- high-risk fields;

- smoke-test URLs.

Этот файл должен обновляться при крупных изменениях архитектуры, схемы данных, команд или roadmap.

## Agent-Compatible Content Model

Каждая управляемая сущность должна иметь стабильные машинные идентификаторы:

- `id` - Payload ID;
- `slug` - публичный URL-идентификатор, если сущность публикуется;
- `external_id` - ID из источника или будущей интеграции;
- `sku` - для товаров;
- `code` - для справочников и controlled values.

Для agent-friendly изменений нужны поля:

- `status`: draft, review, published, archived;
- `revision_note`;
- `last_reviewed_at`;
- `last_reviewed_by`;
- `quality_status`;
- `agent_editable`;
- `agent_lock_reason`;
- `requires_human_approval`;
- `source_of_truth`;
- `validation_errors`;
- `preview_path`.

Все массивы, которые Codex должен менять, должны быть структурированными:

- товары в заявке - array, а не JSON в textarea;
- характеристики - controlled values, а не свободный текст;
- FAQ - массив question/answer;
- блоки страниц - typed blocks;
- внутренние ссылки - relation fields;
- документы - relation fields;
- изображения - media relation fields.

## Agent Change Workflow

Рабочий процесс изменений через Codex:

1. Пользователь формулирует задачу в диалоге.
2. Codex находит связанные записи Payload и показывает, что будет менять.
3. Codex создает draft/revision, не ломая опубликованную версию.
4. Codex запускает проверки:
   - обязательные поля;
   - slug/URL uniqueness;
   - SEO title/description length;
   - canonical/indexing policy;
   - Product/ItemList/FAQ schema.org;
   - отсутствие внутренних служебных терминов в публичном UI;
   - page smoke-test.
5. Codex показывает summary diff и preview URL.
6. Пользователь подтверждает публикацию.
7. Codex публикует изменение и пишет запись в audit log.

Для низкорисковых изменений пользователь может заранее разрешить Codex выполнять публикацию сразу. Но изменения цены, юридических утверждений, документов, сертификатов, реестра, оплаты, доставки и интеграций всегда требуют отдельного подтверждения.

## Agent APIs And Scripts

Помимо UI админки нужны служебные интерфейсы для Codex, Claude Code и других агентов:

- seed/import scripts для загрузки исходного ассортимента в Payload;
- export scripts для выгрузки товаров, категорий, страниц и SEO-полей в JSON/CSV для ревью;
- validation scripts для проверки качества данных;
- preview helpers для открытия публичных страниц после изменения;
- smoke-test scripts для набора ключевых URL;
- migration scripts для изменения схемы коллекций без ручной правки БД.

Предпочтительный подход:

- все изменения схемы выполняются через код коллекций Payload;
- массовые изменения данных выполняются через scripts с dry-run режимом;
- Codex сначала запускает dry-run, затем применяет изменения;
- каждый script выводит список затронутых записей и ошибок.

Минимальный набор будущих scripts:

- `seed:products`;
- `seed:categories`;
- `export:catalog`;
- `validate:catalog`;
- `validate:seo`;
- `validate:schema`;
- `smoke:public-pages`;
- `agent:propose-change`;
- `agent:apply-change`;
- `agent:context`.

`agent:context` должен выводить краткую сводку для нового агента: назначение проекта, текущий статус, ключевые документы, команды, URL, коллекции Payload и правила безопасных изменений.

## Принцип Разделения

В админку выносим:

- данные, которые должен менять менеджер без разработки;
- ассортимент, карточки, характеристики, документы и SEO-тексты;
- настройки публикации, индексации и schema.org;
- заявки, статусы и операционные комментарии;
- глобальные настройки сайта, контактов, аналитики и CTA.

В коде оставляем:

- дизайн-систему;
- структуру React-компонентов;
- бизнес-логику фильтров и расчетов;
- интеграционный код;
- системные ограничения SEO;
- схему валидируемых полей.

Админка не должна превращаться в свободный page builder без ограничений: все ключевые страницы собираются из заранее заданных блоков и валидируемых полей.

## Роли

| Роль | Что делает |
|---|---|
| Администратор | Управляет пользователями, правами, системными настройками, интеграциями. |
| Контент-редактор | Редактирует тексты страниц, статьи, документы, изображения, SEO-поля. |
| Менеджер продаж | Обрабатывает заявки, меняет статусы, добавляет комментарии, видит состав КП. |
| Каталог-менеджер | Ведет товары, категории, характеристики, цены до подключения МойСклад. |
| SEO-специалист | Управляет посадочными, meta, canonical, indexing policy, schema.org, перелинковкой. |

### Характеристики И Справочники

Коллекции:

- `attribute-groups`;
- `attributes`;
- `attribute-options`.

Назначение: чтобы фильтры, карточки и SEO-посадочные использовали controlled values, а не произвольный текст.

Примеры групп:

- монтаж;
- электрика;
- розетки;
- защита;
- мониторинг;
- управление;
- документы;

Каждое значение должно иметь:

- машинный код;
- публичное название;
- альтернативные написания;
- сортировку;
- используется ли в фильтрах;
- разрешено ли создавать индексируемую страницу;
- SEO-шаблон для посадочной.

### Конфигурируемые Фильтры

Фильтры каталога должны управляться из админки. Каталог-менеджер или SEO-специалист должен иметь возможность добавлять, отключать, удалять и переупорядочивать поля фильтров без изменения React-кода.

Коллекции:

- `filter-groups`;
- `filter-fields`;
- `filter-options`;
- `filter-presets`.

`filter-groups`:

- код группы;
- публичное название;
- сортировка;
- активность;
- категории, где группа показывается.

`filter-fields`:

- код поля;
- публичное название;
- тип поля: single select, multi select, range, boolean;
- связанный attribute;
- категории, где поле доступно;
- показывать счетчики;
- пересчитывать счетчики по текущей выдаче;
- разрешить множественный выбор;
- разрешить индексируемые страницы;
- поведение при нулевой выдаче;
- сортировка.

`filter-options`:

- код значения;
- публичное название;
- связанный controlled value;
- alias/синонимы;
- sort order;
- SEO slug;
- indexable allowed;
- active.

`filter-presets`:

- название пресета;
- slug;
- категория;
- набор условий фильтра;
- H1;
- intro;
- SEO title;
- SEO description;
- canonical;
- indexing policy;
- related links.

Правила:

- счетчики фильтров должны пересчитываться по текущему набору выбранных условий;
- опции с нулевой выдачей должны быть disabled, если нет отдельного SEO-сценария;
- добавление нового поля фильтра не должно автоматически создавать индексируемые URL;
- индексируемость фильтр-страницы разрешается только через `filter-presets` или SEO landing;
- каждый фильтр должен иметь stable machine code, чтобы агент мог изменять настройки без визуального UI.

### Schema.org

В админке нужно управлять данными, из которых формируется schema.org:

- Product;
- Offer или отсутствие Offer при "цена по запросу";
- Brand;
- Organization;
- BreadcrumbList;
- ItemList;
- Article;
- FAQPage;
- WebSite;
- SearchAction, если будет поиск.

Обязательное правило: публичные карточки товаров и категории должны оставаться совместимыми со schema.org, даже если данные меняются через админку.

## 8. Права Доступа

Минимальная модель:

- admin: полный доступ;
- editor: контент, SEO, медиа без системных настроек;
- sales: заявки и комментарии;
- catalog_manager: товары, категории, документы;
- seo: SEO-поля, посадочные, статьи, метаданные.
- agent: техническая роль для Codex/API-операций с ограниченными правами, draft-first workflow и обязательным audit log.

Требования:

- публичное API для чтения только опубликованных материалов;
- заявки доступны только авторизованным пользователям;
- удаление товаров и заявок ограничено admin;
- изменения SEO и публикации должны быть видимы в истории.
- agent-роль не может удалять записи, менять production-секреты и публиковать high-risk изменения без подтверждения.

## Audit Log

Нужна отдельная коллекция `admin-change-log`.

Поля:

- `actor_type`: user, agent, script, integration;
- `actor_name`;
- `target_collection`;
- `target_id`;
- `target_label`;
- `change_type`;
- `before_snapshot`;
- `after_snapshot`;
- `diff_summary`;
- `reason`;
- `approval_status`;
- `approved_by`;
- `created_at`.

Назначение:

- восстановить, что именно поменялось;
- понять, почему Codex внес изменение;
- сравнить версию до/после;
- быстро откатить ошибочную правку через повторное применение previous snapshot.

## Критерии Готовности

- В админке есть не только заявки, но и управляемый каталог.
- Менеджер может открыть заявку, понять состав товаров и сменить статус.
- Каталог-менеджер может изменить товар без правки кода.
- SEO-специалист может поменять title, description, H1, canonical и indexing policy.
- Product schema.org и ItemList schema.org формируются из данных Payload.
- Codex может безопасно внести draft-изменение в товар, категорию или страницу, показать diff и preview.
- Каждое agent-изменение сохраняет audit log.
- Публичный сайт не ломается при неполных данных: есть fallback для цены, документов, изображений и характеристик.
- `pnpm lint`, `pnpm typecheck`, `pnpm build` проходят.
- Smoke-test проверяет `/admin/`, `/product/...`, `/catalog/pdu/`, `/b2b/request-quote/`.
