# Design Review Methodology

Дата: 2026-05-15.

## Почему Метод Нужно Изменить

Предыдущее ревью нашло часть проблем, но пропустило блоки на главной, которые были ниже первого экрана: `Популярные входы`, `Страницы, с которых начнется органический трафик`, `RFQ`, `Листинги...`.

Причина: ревью было построено как визуальный проход по контрольным экранам и общая оценка страниц. Такой подход видит композицию, но не гарантирует проверку каждого публичного текстового блока.

## Новый Алгоритм Ревью

### 1. Full-Page Text Inventory

Для каждой проверяемой страницы нужно получить полный DOM/text snapshot и выписать все видимые:

- eyebrow labels;
- H1/H2/H3;
- lead paragraphs;
- CTA;
- карточки перелинковки;
- trust-блоки;
- metric labels;
- footer/header copy.

Нельзя считать страницу проверенной только по первому экрану.

### 2. Public Language Gate

Каждый текст проверяется вопросом: "Это написано для покупателя или для команды проекта?"

Запрещенные публичные маркеры:

- `SEO`;
- `органический трафик`;
- `Conversion`;
- `Trust`;
- `MVP`;
- `RFQ`, если рядом нет расшифровки для пользователя;
- `листинг`, если речь не о технической документации, а о каталоге;
- `страница должна`, `показываем`, `skeleton`, `use-case`;
- любые названия внутренних шаблонов, кластеров или методологии.

### 3. Block-Level JTBD Check

Каждый блок получает одну пользовательскую задачу:

- выбрать товар;
- понять, подходит ли категория;
- запросить КП;
- получить документы;
- проверить надежность производителя;
- перейти к подбору.

Если блок не помогает ни одной задаче, он помечается как удалить или переписать.

### 4. Source-Line Traceability

Для каждого P0/P1-замечания фиксируется источник в коде или контенте:

- файл;
- строка;
- текущий текст;
- предложенный публичный текст.

Без source-line traceability ревью считается неполным.

### 5. Scroll-State Visual Pass

По возможности сохраняются скриншоты:

- first viewport;
- middle content;
- lower content;
- footer area;
- mobile viewport.

Если screenshot tool недоступен или зависает, DOM/text audit остается обязательным и считается основным источником для текстового ревью.

### 6. Automated Marker Sweep

Перед финальным вердиктом выполняется поиск по исходникам и/или DOM:

```bash
rg -n "органичес|SEO|трафик|Conversion|Trust|RFQ|листинг|MVP|должна|показываем|skeleton|use-case" apps/web/src -S
```

Совпадения не всегда являются ошибкой, но каждое публичное совпадение должно быть классифицировано.

### 7. Review Verdict Rules

Страница не может получить `pass`, если:

- есть публичный внутренний язык;
- H1/H2 говорит о механике SEO, а не о задаче пользователя;
- карточки перелинковки показывают demand clusters вместо полезных описаний;
- CTA ведет к действию, но блок не объясняет пользу действия;
- trust-claims не имеют безопасной формулировки или доказательной связки.

## Формат Нового Ревью

Каждое ревью должно включать:

1. Что проверялось.
2. Почему прежняя проверка могла пропустить проблему.
3. Таблицу найденных блоков.
4. P0/P1/P2 findings.
5. Source lines.
6. Предложенные публичные формулировки.
7. Решение: pass / conditional pass / fail.
