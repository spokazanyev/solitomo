# Sitewide Content And Design Review V2

Дата: 2026-05-15.

## Цель

Проверить все публичные страницы Soliton по новой методологии ревью: не по первому экрану и не по общему впечатлению, а по полному публичному тексту страницы, DOM-снимкам ключевых шаблонов, source-line traceability и задачам пользователя.

Это ревью не вносит изменения в интерфейс. Документ фиксирует отчет, причины дефектов и план работ для следующей итерации.

## Методология

Использована методология из `07-build-specifications/design-review-methodology.md`:

- карта публичных URL из `http://localhost:3000/sitemap.xml`;
- SSR text sweep всех публичных URL;
- DOM-снимки и скриншоты репрезентативных шаблонов;
- Public Language Gate для внутренних терминов;
- привязка P0/P1-дефектов к строкам исходного кода;
- проверка задач пользователя: найти товар, понять применимость, запросить КП, найти документы, перейти в B2B-сценарий.

Проверено 102 публичных URL. Ошибки Public Language Gate найдены на 12 URL.

## Общий Вердикт

Сайт функционально движется в правильную сторону: каталог, карточки товаров, заявка на КП, документы, B2B-раздел и SEO-посадочные уже собраны в единую систему.

Но текущая версия не проходит новый content/design QA gate. Причина не в одном блоке главной, а в системной утечке внутренних рабочих терминов в публичный интерфейс.

Главная проблема: служебное поле `demandCluster` и внутренние SEO/SDD-формулировки используются как пользовательский текст. Для поисковой системы это не критическая техническая ошибка, но для живого покупателя и корпоративного заказчика это разрушает доверие: сайт местами говорит языком внутренней SEO-доски, а не языком производителя оборудования.

## Почему Предыдущий Алгоритм Ревью Пропустил Проблему

Предыдущий подход был слишком визуальным и экранным:

- оценивался верх страницы, а проблемные блоки ниже fold оставались вне фокуса;
- не было обязательного SSR/DOM text sweep по всем URL;
- `demandCluster` не был отмечен как потенциально публичное поле;
- ревью не требовало source-line traceability для каждого найденного публичного дефекта;
- проверялись отдельные страницы, а не шаблонные утечки across site.

Новая методология устраняет это через обязательный full-page inventory и marker sweep.

## P1 Findings

### P1. В публичных карточках связанных страниц показывается `demandCluster`

Источник: `apps/web/src/components/page-templates.tsx:74-88`.

`LinkGrid` выводит `item.demandCluster` как описание ссылки. Это техническое поле содержит SEO-кластеры и внутренние ярлыки: `B2B use-case`, `Trust`, `Conversion`, `B2B custom`, `B2B integrators`, `B2B tenders`.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/08-solution.dom.txt`: `B2B use-case`;
- `07-build-specifications/sitewide-review-screenshots-v2/09-company.dom.txt`: `Brand trust`;
- страницы `/company/contacts/` показывают `Conversion`.

Почему это плохо:

- пользователь видит рабочие SEO-ярлыки вместо полезного описания;
- корпоративный покупатель считывает сайт как недоработанный прототип;
- проблема распространяется на все шаблоны, где используется `LinkGrid`.

### P1. На главной остался внутренний SEO-блок про органический трафик

Источник: `apps/web/src/components/page-templates.tsx:355-363`.

Публичный текст:

- `Популярные входы`;
- `Страницы, с которых начнется органический трафик`;
- `Главная направляет пользователя в спросовые категории...`.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/01-home.dom.txt:184`.

Почему это плохо:

- покупателю не нужно знать, что страница построена как SEO-вход;
- блок объясняет внутреннюю механику сайта вместо решения задачи пользователя;
- это была именно та проблема, которую пользователь увидел на главной.

### P1. На главной используется термин `RFQ`

Источник: `apps/web/src/lib/seo/template-content.ts:39-44`.

Публичный текст:

- `RFQ`;
- `заявки на КП по товару или ТЗ`.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/01-home.dom.txt:56`.

Почему это плохо:

- для российского B2B-покупателя понятнее `КП`, `заявка на КП`, `коммерческое предложение`;
- `RFQ` выглядит как внутренний термин, если он не объяснен.

### P1. На главной используется слово `Листинги`

Источник: `apps/web/src/components/page-templates.tsx:319-323`.

Публичный текст:

- `Листинги по монтажу, току, розеткам и функциям...`.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/01-home.dom.txt:58-61`.

Почему это плохо:

- `листинг` - рабочий термин для команды сайта, не коммерческий текст;
- блок должен обещать покупателю быстрый путь к нужному типу PDU, а не описывать структуру каталога.

### P1. В статьях показывается внутренняя перелинковка как публичная сущность

Источник: `apps/web/src/components/page-templates.tsx:590-598`.

Публичный текст:

- `Внутренняя перелинковка из статьи`.

Дополнительная утечка:

- `apps/web/src/lib/seo/seo-registry.ts:412` содержит summary `Ключевая экспертная статья для внутренней перелинковки...`, который виден в DOM статьи.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/07-knowledge.dom.txt:35`;
- `07-build-specifications/sitewide-review-screenshots-v2/07-knowledge.dom.txt:62`.

Почему это плохо:

- статья должна вести к выбору оборудования, а не объяснять SEO-механику;
- экспертность страницы снижается, потому что пользователь видит внутренний термин.

### P1. В B2B-шаблоне показывается `RFQ-макет`

Источник: `apps/web/src/components/page-templates.tsx:708-718`.

Публичный текст:

- `Быстрый RFQ-макет`.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/04-b2b.dom.txt:65`;
- `07-build-specifications/sitewide-review-screenshots-v2/05-rfq.dom.txt:118`.

Почему это плохо:

- это звучит как подпись к wireframe, а не как часть готового сайта;
- для пользователя нужно назвать блок по результату: `Что указать в заявке`, `Данные для КП`, `Быстрый запрос коммерческого предложения`.

### P1. В company-шаблоне виден `B2B-процесс`

Источник: `apps/web/src/components/page-templates.tsx:857-860`.

Публичный текст:

- `...связи с B2B-процессом`.

Наблюдение в DOM:

- `07-build-specifications/sitewide-review-screenshots-v2/09-company.dom.txt:49`.

Почему это плохо:

- формулировка неестественная для покупателя;
- лучше говорить о закупке, документах, реквизитах, производстве и контактах для КП.

### P1. Fallback eyebrow выводит `demandCluster` в hero

Источник: `apps/web/src/components/SeoLandingPage.tsx:195-220`.

Если route не имеет публичного override, `routeEyebrow(route)` возвращает `route.demandCluster`. Это уже проявилось на:

- `/solutions/pdu-dlya-cod/` -> `B2B use-case`;
- `/company/about/` и `/company/production/` -> `Brand trust`;
- `/company/contacts/` -> `Conversion`.

Почему это плохо:

- hero-eyebrow является одним из самых заметных элементов страницы;
- внутренний кластер в hero воспринимается как недоделка.

## P2 Findings

### P2. Trust claims пока слабо подкреплены

Источник: `apps/web/src/lib/seo/template-content.ts:20-36`.

Тексты про 15-летнюю историю, российское производство, реестр и надежность звучат лучше, чем раньше, но им нужны более явные пути к доказательствам:

- ссылка на документы;
- ссылка на раздел производства;
- пояснение, что подтверждение по реестру выдается по конкретным моделям;
- аккуратные формулировки без обещаний, которые нельзя проверить на странице.

### P2. Главная все еще больше похожа на технологический прототип, чем на коммерческий сайт производителя

Первый экран стал чище, но ниже остаются системные карточки и утилитарные блоки. Для современного сайта производителя PDU нужны:

- сильнее визуальная товарная витрина;
- более ясные сценарии: купить серийный PDU, подобрать по стойке, запросить КП по ТЗ;
- больше доказательств производства и документов;
- меньше терминов из проектирования сайта.

### P2. Статьи нужно редактировать как экспертный контент, а не как SEO-заготовки

Некоторые статьи проходят по структуре, но звучат как шаблон. Для органического трафика это недостаточно: статья должна давать самостоятельную пользу и естественно вести к каталогу или заявке.

### P2. Dev overlay может мешать просмотру в локальной среде

Пользователь ранее видел постоянный `Rendering ...` overlay. Это относится к dev-режиму и не является продакшен-контентом, но для демонстраций и UX-ревью лучше использовать production preview или устранить причину частого rerender на форме КП.

## План Изменений

### Этап 1. Убрать системные термины из публичного UI

Задачи:

1. Заменить `routeEyebrow(route)` fallback: не возвращать `route.demandCluster` в UI.
2. Ввести публичные labels для типов страниц: каталог, подбор, статья, документы, компания.
3. Переписать `LinkGrid`: вместо `item.demandCluster` показывать публичное описание маршрута.
4. Добавить helper `routePublicSummary(route)` или поле `publicCardText`, не связанное с SEO-кластером.

Критерий приемки:

- ни один публичный URL не показывает `B2B use-case`, `Trust`, `Brand trust`, `Conversion`, `B2B custom`, `B2B integrators`, `B2B tenders`.

### Этап 2. Переписать проблемные блоки главной

Задачи:

1. Заменить `RFQ` на `КП` или `Заявка на КП`.
2. Заменить `Листинги...` на пользовательский текст про быстрый выбор категории.
3. Заменить блок `Страницы, с которых начнется органический трафик` на коммерческий блок, например `Популярные задачи покупателей`.
4. Убрать любые формулировки про органический трафик и внутреннюю структуру сайта.

Критерий приемки:

- главная проходит marker sweep;
- нижние блоки читаются как витрина производителя, а не как SEO-карта.

### Этап 3. Переписать B2B и company формулировки

Задачи:

1. Заменить `Быстрый RFQ-макет` на `Что указать в заявке на КП`.
2. Заменить `B2B-процесс` на текст про закупку, реквизиты, производство и документы.
3. Проверить все B2B-страницы на термин `RFQ`.
4. Уточнить тексты для закупщиков и интеграторов: КП, счет, документы, сроки, город поставки, повторяемые партии.

Критерий приемки:

- `/b2b/*` и `/company/*` проходят Public Language Gate;
- тексты звучат как готовый коммерческий сайт для юридических лиц.

### Этап 4. Переписать блоки связанных страниц в статьях

Задачи:

1. Заменить `Внутренняя перелинковка из статьи`.
2. Переписать summary в `seo-registry.ts`, если оно выводится в публичном UI.
3. Назвать блок по задаче пользователя: `Перейти к выбору PDU`, `Связанные варианты подбора`, `Следующий шаг`.

Критерий приемки:

- статьи не содержат SEO-терминов;
- связанный блок объясняет, что делать после чтения.

### Этап 5. Усилить trust/proof blocks

Задачи:

1. Добавить ссылки из trust-блоков к документам, производству и заявке на подтверждение по модели.
2. Переписать claim про реестр так, чтобы он не обещал больше, чем может подтвердить страница.
3. Добавить на главную блоки доказательств: производство, документы, реестр, 15-летняя история, работа с юрлицами.

Критерий приемки:

- claims выглядят проверяемыми;
- пользователь понимает, где получить подтверждение для закупки.

### Этап 6. Добавить автоматический публичный copy audit

Задачи:

1. Создать скрипт, который берет URL из sitemap и проверяет SSR HTML на forbidden public markers.
2. Добавить команду в `package.json`, например `pnpm public-copy-audit`.
3. Зафиксировать whitelist для допустимых слов, если они нужны в технической документации или metadata.
4. Включить эту проверку в QA перед демонстрацией.

Критерий приемки:

- новая ошибка такого типа не пройдет без явного исключения;
- ревью больше не зависит только от визуального просмотра.

## Acceptance Criteria Для Следующей Итерации

- Все 102 публичных URL проходят marker sweep без запрещенных публичных терминов.
- `LinkGrid` не выводит `demandCluster`.
- `routeEyebrow` не возвращает SEO-кластеры как пользовательский текст.
- Главная не содержит текстов про органический трафик, листинги, SEO-входы, RFQ.
- B2B-страницы используют `КП`, `заявка`, `коммерческое предложение`, `документы`, `поставка`.
- Статьи не используют формулировки про внутреннюю перелинковку.
- После правок повторяется DOM/SSR audit по всем URL и визуальная проверка ключевых шаблонов.
