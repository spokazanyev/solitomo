# Feature Specification: Унификация выбора доставки в чекауте юрлица

**Feature Branch**: `062-invoice-shipping-unify`

**Created**: 2026-05-27

**Status**: Draft

**Input**: User description: «Изучи выбор доставки при оплате от юридического лица. По идее он должен быть такой же, как для физлица, там мы уже всё отладили. Варианты: (1) Самовывоз; (2) Выбор вариантов через ApiShip; (3) Отправка транспортной компанией покупателя, по его договору. Для (3) внести уточнение в примечание. После выбора стоимость доставки (если не 0) добавляется отдельной строкой в счёт. Если самовывоз или отправка ТК покупателя — в счёте указывается в примечаниях как происходит доставка, в табличную часть не вносится.»

## Clarifications

### Session 2026-05-27

- Q: Какой режим доставки предвыбран по умолчанию при первой загрузке формы счёта? → A: «Через службу доставки» предвыбран (Option A) — сразу рендерится `<AddressForm>`, при валидном адресе появляется список тарифов.
- Q: Что происходит при смене режима, если пользователь уже выбрал ApiShip-тариф? → A: Silent reset (Option A) — ApiShip-выбор (tariff/ПВЗ/cost) сбрасывается без диалога; адрес в AddressForm сохраняется; при возврате в режим ApiShip — пересчёт с нуля.
- Q: Остаётся ли `handoverNote` редактируемым после `paid` (вопреки иммутабельности 051)? → A: Да, исключение из 051 (Option B) — поле остаётся редактируемым операционно (контакт водителя/смена ТК), все изменения логируются в `Order.history` с actor + reason. Финансовая часть заказа (`totals`, позиции, чек 54-ФЗ) — без изменений.
- Q: Обязательно ли поле «контактное лицо получателя» при самовывозе? → A: Обязательное с авто-предзаполнением (Option B) — при выборе режима «Самовывоз» поле автоматически заполняется значением «ФИО + телефон» из блока «Контактное лицо» реквизитов юр-лица; пользователь может изменить или оставить дефолт. Пустое поле → кнопка «Выписать счёт» неактивна.
- Q: Терминология mode-значения «своя ТК» в БД vs аналитике? → A: Полная унификация на `own_carrier` (Option B) — Payload-enum `Order.delivery.method` переименовывается `tc → own_carrier`, выполняется data-migration всех существующих заказов с `method='tc'` в `method='own_carrier'`. Analytics-параметр `mode = own_carrier` (FR-062-40) совпадает с БД. FR-062-52 пересматривается: миграция требуется и описывается отдельным шагом плана.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Закупщик оформляет счёт с доставкой через службу (Priority: P1)

Закупщик юр-лица оформляет счёт на оборудование и хочет получить точную стоимость доставки СДЭК / Boxberry / Почтой / курьером до офиса заранее — чтобы итоговая сумма в счёте уже включала логистику, и не пришлось переделывать счёт после уточнения у менеджера.

**Why this priority**: Это самый частый B2B-кейс для онлайн-каталога средне-крупного оборудования. Сейчас юр-чекаут не предлагает расчёт стоимости вообще: пользователь вводит свободный адрес и выбирает службу из выпадающего списка, но в счёте появляется только сумма позиций без доставки. Менеджеру приходится досчитывать вручную и переоформлять счёт — потеря времени для обеих сторон.

**Independent Test**: Открыть `/cart/checkout/invoice/` с непустой корзиной, выбрать режим «Через службу доставки», ввести валидный адрес офиса в Москве, дождаться появления тарифов, выбрать СДЭК-курьером. Подтвердить, что в сайдбар-сводке и затем в PDF-счёте появляется строка «Доставка: <сумма>», а «Итого к оплате» включает её.

**Acceptance Scenarios**:

1. **Given** в корзине 2 позиции с ценами и пользователь на форме счёта, **When** он выбирает режим «Через службу доставки» и вводит валидный адрес доставки, **Then** появляется список реальных тарифов (СДЭК / Boxberry / Почта / курьерские) с ценой, сроками и значками «дешевле»/«быстрее».
2. **Given** пользователь выбрал тариф «в пункт выдачи» (deliveryType=2), **When** он подтверждает выбор, **Then** появляется выбор конкретного ПВЗ; без выбора ПВЗ кнопка «Выписать счёт» неактивна.
3. **Given** пользователь выбрал валидный ApiShip-тариф с положительной стоимостью, **When** он отправляет форму, **Then** созданный заказ содержит provider/providerKey/tariffId/cost/etaMin/etaMax/addressNormalized/pointId (если применимо), а сгенерированный PDF-счёт показывает «Доставка: <стоимость>» отдельной строкой и включает её в итог.
4. **Given** ApiShip временно недоступен или вернул пустой список тарифов, **When** пользователь видит warning «Расчёт временно недоступен», **Then** кнопка «Выписать счёт» неактивна в этом режиме — пользователь может переключиться на другой режим (своя ТК / самовывоз) и продолжить оформление.

### User Story 2 — Закупщик отгружает по собственному договору с ТК (Priority: P1)

Закупщик имеет действующий корпоративный договор с одной из ТК (DHL, ПЭК, Деловые линии, СДЭК-договор и т.п.) и оплачивает логистику отдельно. Он должен выписать счёт без строки «Доставка», но явно указать, что отгрузка пойдёт через его ТК — чтобы менеджер при сборке знал, куда передать груз и какие реквизиты нанести на накладной.

**Why this priority**: Типичный B2B-кейс для крупных закупок (вес/габариты вне сетки ПВЗ ApiShip) или для региональных компаний со своей логистикой. Сейчас юр-чекаут предлагает опцию «Транспортной компанией», но никак не позволяет указать, какой именно ТК и по какому договору — менеджеру приходится перезванивать.

**Independent Test**: Открыть `/cart/checkout/invoice/` с непустой корзиной, выбрать режим «Транспортной компанией покупателя», заполнить поле уточнения («ПЭК, договор № 4567 от 12.01.2025, контакт водителя +7 9XX XXX XX XX»), отправить форму. Подтвердить, что в PDF-счёте нет строки «Доставка», «Итого к оплате» = сумма позиций (с НДС), а в блоке «Примечания» отображается заполненный текст.

**Acceptance Scenarios**:

1. **Given** пользователь выбрал режим «Транспортной компанией покупателя», **When** он пытается отправить форму с пустым полем уточнения, **Then** кнопка «Выписать счёт» неактивна.
2. **Given** пользователь заполнил поле уточнения ТК, **When** он отправляет форму, **Then** созданный заказ имеет `delivery.method = "own_carrier"`, `delivery.cost = 0` и `delivery.handoverNote` = введённый текст.
3. **Given** заказ создан в режиме «своя ТК», **When** генерируется PDF-счёт, **Then** в табличной части итогов **нет** строки «Доставка», «Итого к оплате» равно «Сумма позиций» (с НДС), а в конце документа в блоке «Примечания» отображается «Отгрузка транспортной компанией покупателя: <handoverNote>».

### User Story 3 — Закупщик забирает заказ самовывозом (Priority: P2)

Закупщик находится в том же городе, что и склад поставщика, и хочет забрать оборудование сам — для экономии и контроля сроков. В счёте не должно быть строки «Доставка», но в примечаниях обязательно — адрес склада, чтобы водитель/менеджер закупщика не звонил уточнять.

**Why this priority**: Используется реже, чем US1/US2, но регулярно — особенно для срочных закупок в Московском регионе. Поведение уже частично существует (опция `pickup` в выпадающем списке), но без передачи адреса склада в счёт и без явного UX.

**Independent Test**: Открыть `/cart/checkout/invoice/` с непустой корзиной, выбрать режим «Самовывоз», по желанию заполнить поле «Контактное лицо получателя», отправить форму. Подтвердить, что в PDF-счёте нет строки «Доставка», а в блоке «Примечания» отображается адрес склада из настроек компании.

**Acceptance Scenarios**:

1. **Given** пользователь выбрал режим «Самовывоз», **When** ни одно дополнительное поле не заполнено, **Then** кнопка «Выписать счёт» активна (при условии заполненных контактов и реквизитов компании).
2. **Given** пользователь отправляет форму в режиме самовывоза, **When** заказ создан, **Then** `delivery.method = "pickup"`, `delivery.cost = 0`, `delivery.handoverNote` = либо пустой, либо заполненный текст контакта.
3. **Given** заказ создан в режиме самовывоза, **When** генерируется PDF-счёт, **Then** строки «Доставка» в табличной части нет, в блоке «Примечания» отображается «Самовывоз со склада: <актуальный адрес склада>» + строка с handoverNote, если поле было заполнено.

### User Story 4 — Менеджер видит корректную сводку отгрузки в счёте (Priority: P2)

Менеджер при обработке заказа открывает PDF-счёт и за 5 секунд понимает: какой режим отгрузки выбрал клиент, какие у клиента дополнительные пожелания/реквизиты, и какая сумма должна быть оплачена.

**Why this priority**: Качество счёта влияет на скорость обработки и количество переспрашивающих звонков, но это побочный эффект корректной реализации US1/US2/US3. Отдельная история нужна для явной проверки формата документа.

**Independent Test**: Прогнать 3 типа заказов (ApiShip / своя ТК / самовывоз) и визуально сравнить три PDF: должны различаться только наличием строки «Доставка» в итогах и текстом в блоке «Примечания».

**Acceptance Scenarios**:

1. **Given** заказ с ApiShip-доставкой стоимостью 850 ₽, **When** менеджер открывает PDF, **Then** в табличной части после «Сумма позиций» и «НДС» есть строка «Доставка: 850,00 ₽», блок «Примечания» включает только стандартные строки (оплата по реквизитам, НДС-политика, директор, М.П.).
2. **Given** заказ со своей ТК и handoverNote, **When** менеджер открывает PDF, **Then** строки «Доставка» нет, в блоке «Примечания» сразу после стандартного текста про оплату появляется выделенная подстрока «Отгрузка транспортной компанией покупателя: …».
3. **Given** заказ с самовывозом, **When** менеджер открывает PDF, **Then** строки «Доставка» нет, в блоке «Примечания» появляется «Самовывоз со склада: <адрес>» и при наличии — handoverNote.

---

### Edge Cases

- **ApiShip недоступен или вернул пустые тарифы для крупного груза** — пользователь видит warning от `DeliveryBlock` и может переключиться на режим «своя ТК» или «самовывоз»; форма не блокирует выписку счёта в этих режимах.
- **handoverNote очень длинный (несколько абзацев)** — поле принимает до 1000 символов; в PDF блок «Примечания» переносится на следующие строки PDFkit; превышение лимита блокирует отправку формы.
- **Пользователь сменил режим после выбора ApiShip-тарифа** — все ApiShip-поля (provider/tariffId/cost/...) сбрасываются на сервере, в Order сохраняется только то, что соответствует финальному режиму.
- **`actualAddress` в настройках компании ещё с TODO-placeholder** — в блоке «Примечания» PDF используется `legalAddress`, либо (если и он TODO) — строка «Адрес склада уточнит менеджер».
- **Существующий заказ в БД с `method = "cdek"` и без `handoverNote`** (создан до этой фичи) — PDF продолжает рендериться так же, как до изменений (строка «Доставка», если `cost > 0`, без блока «Примечания»).
- **Пользователь нажимает «Выписать счёт» в момент пересчёта тарифов** — кнопка остаётся неактивной до завершения расчёта; либо (если `cost` ещё не зафиксирован) форма не отправляется.

## Requirements *(mandatory)*

### Functional Requirements

**Выбор режима доставки (UI)**:

- **FR-062-01**: Форма счёта МУСТ предлагать ровно три взаимоисключающих режима доставки: «Самовывоз», «Через службу доставки», «Транспортной компанией покупателя».
- **FR-062-02**: Режим должен переключаться без потери уже заполненных контактных данных и реквизитов компании.
- **FR-062-03**: По умолчанию выбран режим «Через службу доставки» (наиболее частый кейс), но пользователь сразу видит все три варианта.
- **FR-062-04**: В режиме «Через службу доставки» форма МУСТ показывать тот же UX расчёта, что и физлицовый чекаут: поле адреса с подсказками DaData, валидация адреса, список тарифов с ETA и значками, выбор ПВЗ для тарифов «в пункт выдачи».
- **FR-062-05**: В режиме «Транспортной компанией покупателя» форма МУСТ показать обязательное многострочное поле «Уточнение по отгрузке» (название ТК, договор, контакт) с лимитом до 1000 символов.
- **FR-062-06**: В режиме «Самовывоз» форма МУСТ показать **обязательное** поле «Кто заберёт (ФИО + телефон) / комментарий» с лимитом до 1000 символов; никакие другие поля адреса не отображаются. Поле **автоматически предзаполняется** значением «`<ФИО контактного лица>`, тел. `<телефон контактного лица>`» из блока «Контактное лицо» реквизитов юр-лица (если эти поля заполнены к моменту выбора режима); пользователь может изменить или оставить дефолт. При пустом поле кнопка «Выписать счёт» неактивна.

**Валидация и состояния кнопки**:

- **FR-062-10**: Кнопка «Выписать счёт» МУСТ оставаться неактивной, если:
  - реквизиты компании / контакты не заполнены (как сейчас);
  - выбран режим «Через службу доставки», но адрес невалиден или тариф не выбран;
  - выбран режим «Через службу доставки» с тарифом «в ПВЗ» и не выбран конкретный ПВЗ;
  - выбран режим «Транспортной компанией покупателя», но поле уточнения пусто;
  - выбран режим «Самовывоз», но поле «Кто заберёт» пусто (после ручного стирания авто-предзаполненного значения);
  - не дана отметка о согласии (PDPA + оферта, FR-5712 из 057).
- **FR-062-11**: При смене режима форма МУСТ выполнить silent reset специфичных для предыдущего режима полей **без подтверждающего диалога**:
  - handoverNote из «своей ТК» сбрасывается при уходе на «самовывоз» (и наоборот);
  - выбранный ApiShip-тариф (tariff, cost, pointId, pointAddress) сбрасывается при уходе в «самовывоз» или «свою ТК»;
  - **значение адреса в `<AddressForm>` сохраняется** (не сбрасывается) — при возврате в режим «Через службу доставки» пользователь видит ранее введённый адрес и автоматический пересчёт тарифов.

**Сохранение в Order**:

- **FR-062-20**: API заказов МУСТ принимать опциональное поле `delivery.handoverNote` (строка) и сохранять его в `Order.delivery.handoverNote`.
- **FR-062-21**: API заказов МУСТ нормализовать `delivery.method`: для режима ApiShip — реальный `providerKey` (`cdek`/`boxberry`/`russian-post` или соответствующий fallback), для режима «своя ТК» — `own_carrier` (переименовано из `tc`, см. FR-062-52), для режима «самовывоз» — `pickup`.
- **FR-062-22**: Для режима ApiShip API МУСТ сохранить расширенные поля доставки: `provider`, `providerKey`, `tariffId`, `deliveryType`, `pickupType`, `pointId`, `pointAddress`, `cost`, `etaMinDays`, `etaMaxDays`, `addressNormalized` — теми же значениями и в тех же местах, что и для физлицового чекаута.
- **FR-062-23**: Для режимов `pickup` и `own_carrier` API МУСТ записать `delivery.cost = 0` и не записывать ApiShip-специфичные поля (provider остаётся в значении по умолчанию `fallback`, остальные — пустые/нулевые).
- **FR-062-24**: Серверная проверка `method=own_carrier` без `handoverNote` — отклонять с HTTP 400 `MISSING_HANDOVER_NOTE` (защита от обхода UI-валидации). Аналогичная проверка для `method=pickup` (FR-062-06 делает handoverNote обязательным и для самовывоза).

**Счёт PDF (`/api/invoice/[orderId]/`)**:

- **FR-062-30**: Если `delivery.method` относится к ApiShip-тарифу (`cdek`/`boxberry`/`russian-post`/курьерские/fallback_*) И `delivery.cost > 0`, PDF МУСТ отображать строку «Доставка: <cost>» в табличной части итогов и включать её в «Итого к оплате».
- **FR-062-31**: Если `delivery.method ∈ {pickup, own_carrier}`, PDF МУСТ **не** добавлять строку «Доставка» в табличную часть; «Итого к оплате» равно «Сумма позиций» (с НДС).
- **FR-062-32**: PDF МУСТ содержать блок «Примечания» (после строки «Оплата производится по реквизитам поставщика…» и до подписи директора):
  - для `pickup`: «Самовывоз со склада: <actualAddress, либо legalAddress, либо плейсхолдер «уточнит менеджер»>. Получатель: <handoverNote>»;
  - для `own_carrier`: «Отгрузка транспортной компанией покупателя: <handoverNote>»;
  - для ApiShip-режима — блок «Примечания» не показывается (поведение как сейчас).
  - **Для существующих заказов** с legacy-значением `method='tc'` (на случай, если миграция не успела отработать в момент рендера) PDF МУСТ применять то же поведение, что для `own_carrier`.
- **FR-062-33**: Блок «Примечания» МУСТ визуально выделяться (жирный заголовок «Примечания» с подчёркиванием по аналогии с «Поставщик»/«Плательщик»).

**Аналитика (058)**:

- **FR-062-40**: При смене режима доставки МУСТ генерироваться событие `shipping_mode_changed` с параметром `mode ∈ {pickup, apiship, own_carrier}` и `checkout_type = "legal"`.
- **FR-062-41**: Событие `checkout_step_shipping` (FR-121 из 058) МУСТ передавать `shipping_mode` в параметрах при первом достижении шага.
- **FR-062-42**: При финальном выборе ApiShip-тарифа МУСТ продолжать стрелять `add_shipping_info` с детальными параметрами (provider, cost) — поведение наследуется от текущего физлицового кода.

**Совместимость и миграция**:

- **FR-062-50**: Существующие заказы в БД, созданные до этой фичи, МУСТ корректно отображаться в админке Payload (поле `handoverNote` опциональное, пустое значение не вызывает ошибок).
- **FR-062-51**: Существующие заказы МУСТ корректно генерировать PDF-счёт. Заказы с `method='cdek'/'boxberry'/'russian-post'` (и `cost > 0`) рендерятся с прежней строкой «Доставка» в табличной части. Заказы с `method='tc'`, не успевшие пройти миграцию переименования, рендерятся по правилу для `own_carrier` (FR-062-32) — блок «Примечания» добавляется, если есть `handoverNote`, иначе пропускается.
- **FR-062-52**: Требуется однократная data-migration переименования: все существующие записи `Order.delivery.method = 'tc'` обновляются в `'own_carrier'` (transactional batch update). Аналогичное переименование на уровне Payload-схемы (enum option). Migration МУСТ быть idempotent (повторный прогон — no-op).
- **FR-062-53**: Никакая структурная миграция полей не требуется; поле `handoverNote` — опциональное расширение схемы, добавляется через стандартный Payload-механизм. Только переименование enum-значения требует data-update (FR-062-52).

**Согласие и серверные проверки**:

- **FR-062-60**: Существующее требование `consent: true` (FR-5712 из 057) сохраняется неизменным.
- **FR-062-61**: Поле `delivery.handoverNote` МУСТ оставаться редактируемым через админ-UI (Payload) и серверный API **даже после перехода Order в `paid`** — явное исключение из иммутабельности 051. Все изменения логируются в `Order.history` (actor email + timestamp + previous/new value). Финансовая часть заказа (`totals`, `items`, чек 54-ФЗ, `payment.*`) остаётся иммутабельной как и прежде.

### Key Entities *(include if feature involves data)*

- **Order.delivery (расширение)**: новое опциональное текстовое поле `handoverNote` (≤ 1000 символов). Семантика: «свободный комментарий о способе передачи груза» — используется только для режимов `pickup` (контактное лицо/комментарий получателя) и `own_carrier` (название ТК + договор + контакт), для других режимов остаётся пустым. **Редактируется и после `paid`** (исключение из 051-immutability, FR-062-61), все изменения логируются в `Order.history`.
- **Order.delivery.method (переименование значения)**: набор значений `pickup | cdek | boxberry | russian-post | own_carrier` (последнее переименовано из `tc`). Все существующие заказы с `method='tc'` мигрируются на `own_carrier` (FR-062-52).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-062-01**: 100% B2B-чекаутов с режимом «Через службу доставки» выписывают счёт с заполненной строкой «Доставка» — без обращения менеджера для досчёта стоимости.
- **SC-062-02**: Доля заказов со счётом, который пришлось переоформлять из-за уточнения стоимости доставки, снижается ≥ на 80% относительно baseline (по корпоративной отчётности менеджера за месяц до и после релиза).
- **SC-062-03**: 100% B2B-заказов с режимом «Транспортной компанией покупателя» (`own_carrier`) и режимом «Самовывоз» (`pickup`) содержат заполненное поле `handoverNote` (≥ 20 символов для own_carrier, ≥ 10 для pickup за счёт авто-предзаполнения) — без пустых заглушек.
- **SC-062-04**: Среднее время оформления B2B-счёта от попадания на форму до нажатия «Выписать счёт» снижается не более чем на 10% (новый UI не должен замедлить процесс) и не увеличивается более чем на 30% (допустимый предел для нового шага выбора режима).
- **SC-062-05**: Воронка чекаута: `checkout_step_shipping → checkout_step_payment_method` для `checkout_type=legal` показывает event `shipping_mode_changed` хотя бы в 90% сессий, дошедших до выбора способа доставки.
- **SC-062-06**: 0 регрессий в PDF-счётах: все существующие заказы из истории продолжают рендериться без ошибок (проверка автоматическая на seed-данных + manual smoke на 5 случайных прошлых заказах).
- **SC-062-07**: Data-migration `method='tc' → 'own_carrier'` отрабатывает 100% существующих записей без падений; idempotent (повторный запуск — no-op); до и после миграции PDF старых заказов выглядит идентично (визуальный diff = 0 пикселей).

## Assumptions

- **Адрес склада для самовывоза** — берётся из существующего сервиса `getCompanyContacts()` (поле `actualAddress`, fallback на `legalAddress`); работа с этим источником в скоупе не меняется.
- **Лимит handoverNote = 1000 символов** — разумный дефолт; покрывает «название ТК + договор + контакт» с большим запасом.
- **Дефолтный режим в UI** — «Через службу доставки» (наиболее частый кейс), но пользователь сразу видит все три варианта.
- **ApiShip-fallback** — режим уже умеет работать с пустым/частичным результатом ApiShip (warnings в `DeliveryBlock` от 047); поведение наследуется без изменений.
- **PDF-движок** — текущий `pdfkit` достаточен для добавления блока «Примечания»; никакого перехода на HTML-to-PDF не требуется.
- **CRM-sync (048)** — `crmSettings.enabled=false` на запуске, в Twenty опционально передадим `handoverNote` в `description` opportunity (но это в скоупе **отложено**, как и сам Twenty).
- **Возврат стоимости при отмене заказа (053)** — `delivery.cost` уже учитывается в `Order.totals.total`; refund для ApiShip-доставки работает по существующей логике, для `pickup`/`own_carrier` доставочной части в сумме просто нет.
- **Email-уведомления (049)** — шаблон T-002-invoice (генерация PDF) автоматически использует обновлённый `/api/invoice/[orderId]/`; никаких изменений в email-тексте не требуется.
- **Backward compatibility** — поле `handoverNote` опциональное, для него миграция данных не нужна. Однако переименование `delivery.method='tc' → 'own_carrier'` требует **однократной idempotent data-migration** (FR-062-52); код PDF-рендера и API дополнительно толерантен к legacy-значению `tc` на переходный период (FR-062-51).

## Dependencies *(internal references)*

- **047-delivery-checkout-apiship**: переиспользование `DeliveryBlock`, `AddressForm`, `PointSelector`, `/api/shipping/calculate`. Эта спека не меняется — мы её клиенты.
- **055/056 yookassa**: чекаут юр-лица создаёт заказ со статусом `awaiting_payment`, оплата по счёту вне ЮKassa — никаких изменений в payment-flow.
- **057 consent**: чекбокс согласия уже встроен в `OrderSummaryCard`; никаких изменений на стороне 057 не требуется.
- **058 analytics**: добавляется одно новое событие `shipping_mode_changed`; остальная funnel-аналитика наследуется.
- **061 unified-checkout-summary**: `OrderSummaryCard` уже умеет переключать `showDeliveryLine` — будем включать его при ApiShip-режиме, выключать для `pickup`/`own_carrier`.

## Out of Scope

- Серверная привязка пользователя к ТК-договору (DHL/ПЭК — никакой синхронизации с системами ТК).
- Многократная отгрузка одного заказа разными способами (один заказ — один режим).
- Изменение `/api/shipping/calculate` или провайдеров ApiShip / fallback (047).
- Изменение схемы CRM-sync (048) — `handoverNote` пробросится в Twenty `opportunity.description` отдельной задачей после активации Twenty.
- Изменение шаблонов email (049) — текущий шаблон T-002-invoice использует обновлённый PDF без изменений.
- UI для админа Payload (поле `handoverNote` добавляется как стандартный `textarea`, без кастомных компонентов).
- Локализация (EN-метки добавляются по существующему паттерну `adminLabel(RU, EN)`, тексты счёта остаются по-русски, как сейчас).
