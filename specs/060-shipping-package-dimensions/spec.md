# Feature Specification: Учёт реального веса и габаритов товаров при расчёте доставки

**Feature Branch**: `060-shipping-package-dimensions`

**Created**: 2026-05-26

**Status**: Draft

**Input**: User description: "Правильный учёт веса и габаритов товаров при расчёте стоимости доставки. Сейчас для всех товаров используются дефолтные значения (1.5 кг, 30×20×15 см), quantity не учитывается при формировании мест."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Покупатель видит реалистичную стоимость доставки (Priority: P1)

Покупатель добавляет в корзину тяжёлый или крупногабаритный PDU (например, вертикальный 4U длиной 1.5 м, весом 12 кг). На странице чекаута, после ввода адреса доставки, он видит **корректную** стоимость доставки для такого груза — пропорциональную его реальной массе и габаритам, а не заниженную дефолтную «маленький пакет 1.5 кг».

**Why this priority**: Это главная ценность всей фичи. Сейчас занижение веса/габаритов приводит к двум последствиям: (1) клиент видит цену меньше реальной, делает заказ — а после реальной сортировки у перевозчика тариф пересчитывается, и компания вынуждена либо доплачивать из своего кармана, либо возвращаться к клиенту с дополнительным счётом; (2) для крупногабаритных товаров посылка может вообще не пройти через ПВЗ с ограничениями по размеру, и заказ застрянет на этапе передачи.

**Independent Test**: Можно реализовать без админ-UI: задать физические параметры для нескольких ключевых SKU напрямую в БД, а затем проверить что расчёт доставки для них даёт отличный (выше) результат, чем без этих параметров. Тестируется через UI checkout-формы или прямым вызовом API расчёта доставки.

**Acceptance Scenarios**:

1. **Given** в каталоге есть товар с физическим весом 12 000 г и габаритами 1500×100×100 мм, **When** покупатель добавляет его в корзину (количество 1) и указывает адрес доставки в другой город, **Then** в варианте «Курьером до двери» отображается стоимость доставки выше, чем была бы при дефолтных параметрах (1500 г, 300×200×150 мм), и она соответствует фактическому тарифу перевозчика для такого груза.

2. **Given** в каталоге есть товар с физическими параметрами и второй товар без них, **When** покупатель добавляет оба в одну корзину, **Then** расчёт доставки использует реальные параметры для первого товара и дефолтные значения для второго, и не падает с ошибкой.

3. **Given** покупатель уже видит стоимость доставки в корзине, **When** администратор обновил физические параметры товара в каталоге, **Then** при следующем расчёте (например, после повторного захода или изменения адреса) стоимость доставки пересчитывается с новыми параметрами — старый закешированный результат не используется.

---

### User Story 2 — Администратор заполняет физические параметры товара (Priority: P2)

Контент-менеджер открывает карточку товара в админ-панели и видит выделенную секцию «Физические параметры упаковки» с понятными полями: масса, длина, ширина, высота. Заполняет значения, валидация подсказывает ему если ввёл число вне разумного диапазона. После сохранения товар доступен в каталоге с новыми параметрами, и они автоматически используются в расчёте доставки.

**Why this priority**: Без этого UX администратор не может управлять данными — придётся править БД руками. P2, потому что технически P1 работает и без UI (хотя operationally сложен).

**Independent Test**: Открыть карточку товара в админке, заполнить поля, сохранить. Проверить что в каталоге значения видны и в расчёте доставки используются. Валидация — попробовать ввести отрицательное число, ноль, очень большое значение — увидеть сообщение об ошибке.

**Acceptance Scenarios**:

1. **Given** администратор находится в карточке товара в админ-панели, **When** он открывает секцию «Физические параметры упаковки» и вводит значения для массы (в граммах) и трёх измерений (в миллиметрах), **Then** при попытке сохранения с положительными значениями в разумных пределах система принимает данные.

2. **Given** администратор открывает карточку существующего товара без заполненных физических параметров, **When** он смотрит секцию параметров, **Then** видит явную пометку «не заполнено — используются дефолтные значения», и предупреждение в верхней части карточки.

3. **Given** администратор ввёл значение вне допустимого диапазона (например, отрицательную массу или вес более 200 кг), **When** он пытается сохранить, **Then** система отклоняет сохранение и показывает понятное сообщение об ошибке с указанием допустимого диапазона.

4. **Given** товар сохранён без физических параметров (любое из полей пустое), **When** другие данные (цена, описание, картинки) корректны, **Then** сохранение проходит успешно — физические параметры остаются опциональными.

### User Story 3 — Партионный заказ учитывается корректно (Priority: P3)

Покупатель заказывает 5 одинаковых PDU. В расчёт доставки идут реальные параметры пятикратно: общий вес посылки = 5 × вес единицы, перевозчик понимает что это 5 мест, а не одно. Стоимость доставки масштабируется линейно с количеством.

**Why this priority**: Партионные заказы — частный случай типа B2B-закупок, основной поток. Сейчас баг занижает стоимость в N раз для таких заказов. P3, потому что задача не блокирует фичу (P1 даёт основную ценность), но дополняет её.

**Independent Test**: Через UI checkout-формы добавить один и тот же товар в количестве 5 штук. В расчёте увидеть стоимость заметно выше, чем для одной штуки. Сравнить с ситуацией qty=1.

**Acceptance Scenarios**:

1. **Given** в каталоге есть товар с физическим весом 2 000 г и габаритами 400×200×150 мм, **When** покупатель добавляет 5 единиц этого товара в корзину, **Then** при расчёте доставки система передаёт перевозчику 5 отдельных мест, каждое с этими параметрами.

2. **Given** в корзине 3 единицы товара А и 2 единицы товара Б, **When** покупатель видит расчёт доставки, **Then** общая стоимость соответствует сумме отправки 5 мест с правильными параметрами для каждого товара.

3. **Given** в корзине одна единица товара, для которой стоимость доставки составляет некоторую сумму X, **When** покупатель меняет количество на 2, **Then** новая стоимость доставки явно больше X (ориентировочно близко к 2×X с учётом возможной скидки перевозчика за объём).

---

### Edge Cases

- **Товар без физических параметров**: используются дефолтные значения из настроек интеграции (текущие 1.5 кг, 30×20×15 см). Расчёт не падает, клиент получает оценочную цифру (поведение как сейчас).
- **Все товары в корзине без параметров**: расчёт работает полностью на дефолтах — это эквивалент текущего поведения, обратной совместимости.
- **Очень большая партия (например, qty=50)**: перевозчик может не вернуть тариф или отдать ошибку. Система должна обработать это так же, как любую другую ошибку расчёта — показать предупреждение «стоимость уточнит менеджер», заказ не блокировать.
- **Товар с экстремально большими габаритами**: если хотя бы одно измерение превышает лимит ПВЗ выбранного перевозчика, тариф «в ПВЗ» может стать недоступным. Это уже корректно обрабатывается логикой выбора рейтов — но новые данные могут впервые выявить эту ситуацию для существующих товаров.
- **Импорт нового товара без физических параметров**: товар сохраняется (поля опциональные), но при первом расчёте использует дефолты. Администратор увидит предупреждение в карточке.
- **Изменение параметров товара уже после того, как клиент видит цену**: повторный заход в корзину должен показать пересчитанную цену (кеш расчёта должен инвалидироваться при изменении любого из физических параметров любого товара в корзине).
- **Передача данных в реальную отправку (после оплаты)**: при создании отправления у перевозчика должны использоваться те же реальные параметры (а не «лимит 1.5 кг»), иначе разойдётся то что показано клиенту с тем что отправлено на перевозчика.

## Requirements *(mandatory)*

### Functional Requirements

**Группа A — Хранение и админ-интерфейс параметров товара:**

- **FR-001**: Каталог товаров MUST поддерживать опциональные физические параметры упаковки для каждой единицы товара: масса, длина, ширина, высота.
- **FR-002**: Админ-карточка товара MUST содержать выделенную секцию «Физические параметры упаковки» с понятными подписями и подсказками о единицах измерения.
- **FR-003**: Система MUST валидировать введённые значения: все поля — положительные целые числа в разумных пределах для упаковок (от 1 г до 200 000 г для массы; от 1 мм до 2 000 мм для каждого из измерений). При нарушении — отклонять сохранение с явным сообщением об ошибке.
- **FR-004**: Если хотя бы одно из четырёх физических полей пустое, товар считается «без физических параметров» — при сохранении ошибки нет, но в карточке отображается предупреждение «используются дефолтные значения доставки».
- **FR-005**: Список товаров в админке MUST иметь визуальный индикатор (например, бейдж/иконка) для товаров без заполненных физических параметров, чтобы администратор мог быстро найти и заполнить пробелы.

**Группа B — Использование параметров в расчёте доставки:**

- **FR-006**: При расчёте стоимости доставки система MUST использовать физические параметры конкретного товара из каталога, если они заполнены. Если хотя бы одно из четырёх полей пустое — для этого товара применяются дефолтные значения из настроек интеграции с перевозчиком (текущее поведение).
- **FR-007**: При формировании запроса к перевозчику система MUST передавать каждую единицу товара в корзине как отдельное место (если в корзине лежит 5 одинаковых SKU с весом 2 кг — передаётся 5 мест по 2 кг, не 1 место 2 кг и не 1 место 10 кг).
- **FR-008**: При формировании реального отправления у перевозчика (создание waybill после оплаты) система MUST использовать те же физические параметры, что использовались при расчёте показанной клиенту цены. Расхождения между расчётом и реальной отправкой не допускаются.
- **FR-009**: Расчёт доставки MUST корректно работать со смешанной корзиной, где часть товаров имеет заполненные физические параметры, а часть — нет: для каждого товара параметры берутся независимо.

**Группа C — Инвалидация кеша и консистентность:**

- **FR-010**: Кеш расчёта доставки MUST инвалидироваться при изменении физических параметров любого товара в корзине покупателя — следующий расчёт делается заново с актуальными данными.
- **FR-011**: Изменение физических параметров товара в админ-панели MUST вступать в силу для новых расчётов в течение разумного времени (без необходимости вручную чистить кеш или перезапускать сервис).

**Группа D — Совместимость:**

- **FR-012**: Существующие товары в каталоге без физических параметров MUST продолжать работать в чекауте без вмешательства администратора: расчёт идёт по дефолтам, как и сейчас.
- **FR-013**: Существующие заказы в системе (созданные до этой фичи) MUST оставаться валидными — миграция не должна ломать их связи или историю.

### Key Entities

- **Товар (Product)**: единица каталога. Расширяется опциональной группой физических параметров упаковки: масса единицы товара (в граммах) и три измерения упаковки одного экземпляра (в миллиметрах). Параметры описывают именно упаковку одной штуки готовой к отгрузке (с упаковочной коробкой), не «голый» товар.
- **Дефолтные параметры (Shipping Defaults)**: существующие настройки интеграции с перевозчиком. Используются как fallback для товаров без заполненных параметров и не меняются этой фичей.
- **Место отправления (Shipping Place)**: единица передаваемая перевозчику в API расчёта/создания заказа. Производное от пары (товар, единица из корзины) — на каждую штуку в корзине создаётся одно место с параметрами товара (или с дефолтами, если параметры товара не заполнены).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для топ-10 самых заказываемых SKU в каталоге физические параметры заполнены и используются в расчёте доставки — стоимость доставки для них в чекауте больше не отличается от реальной стоимости у перевозчика более чем на ±5%.

- **SC-002**: При партионном заказе (qty=5 одного SKU) показанная клиенту стоимость доставки масштабируется пропорционально количеству: разница между qty=1 и qty=5 составляет не менее 3.5× от стоимости одной единицы (с учётом возможной нелинейной скидки за объём от перевозчика, точное значение зависит от тарифа).

- **SC-003**: При смешанной корзине из товара с физическими параметрами и товара без них расчёт доставки завершается успешно (без ошибок и без значения «По запросу») — система использует реальные параметры для одного товара и дефолты для другого.

- **SC-004**: Администратор, не имеющий технического опыта, может заполнить физические параметры одного товара в админ-панели за время менее 2 минут с момента открытия карточки до сохранения.

- **SC-005**: Через 1 месяц после выпуска фичи доля заказов, по которым перевозчик доплатил после реальной сортировки (т.е. изначальная оценка была занижена), снизилась минимум на 70% относительно периода до фичи.

- **SC-006**: Существующие 66 опубликованных товаров продолжают отображаться и продаваться в каталоге сразу после выкатки фичи (до того, как администратор успел заполнить новые поля) — никаких визуальных артефактов, ошибок или невозможности оформить заказ.

## Assumptions

- **Единицы измерения**: масса хранится в граммах, габариты в миллиметрах. Это обеспечивает целочисленное представление без потерь точности (даже для маленьких блоков 5×5×5 см и крупных PDU длиной 1.5 м), и позволяет точную конвертацию в форматы любого перевозчика (граммы ↔ кг, миллиметры ↔ сантиметры) без округлений на уровне хранения.
- **Параметры описывают упаковку, не «голый» товар**: то есть масса 8 кг — это PDU + его транспортная упаковка/коробка/паллет, а не вес устройства из техпаспорта. Эти данные владелец каталога вводит после взвешивания готовой к отгрузке посылки.
- **Bulk-import (CSV/XLSX) физических параметров для существующих 66 товаров — out of scope этой фичи**. Это операционная задача владельца каталога: заполнить параметры через админ-панель карточку за карточкой. Если в будущем накопится потребность — отдельная фича.
- **Кеш расчёта доставки уже учитывает физические параметры в ключе** (fingerprint от items с полями weight/length/width/height добавлен в недавней правке). Эта фича лишь поставляет реальные значения в этих полях вместо undefined — никаких новых изменений в логике инвалидации кеша не требуется.
- **Реальные пределы для валидации полей** взяты исходя из физических ограничений упаковок: масса 1 г–200 кг (200 000 г) покрывает диапазон от лёгких розеток-аксессуаров до тяжёлых паллетных PDU; габариты 1 мм–2 000 мм (2 м) покрывают вертикальные стоечные блоки.
- **Сами товары не меняют свою сущность** — это та же коллекция продуктов, та же модель данных, просто с дополнительными опциональными полями. Существующие связи (корзина→товар, заказ→товар, RFQ→товар) сохраняются как есть.
- **Изменения коснутся только flow купли B2C** (страница checkout с предоплатой). Логика RFQ (запрос коммерческого предложения) физических параметров не использует и остаётся неизменной.
- **Дефолтные значения остаются как safety-net** — они не должны исчезнуть после фичи. Если у товара пропустили заполнить параметры — он всё равно отправляется в расчёт с дефолтами, а не падает с ошибкой.
- **Параметр «единица упаковки = единица товара»**: в этой фиче не моделируем сценарий когда несколько единиц одного товара объединяются в одну транспортную коробку («10 розеток в одной коробке 30×40×20 см»). Каждая единица товара = отдельное место. Если в будущем понадобится оптимизация упаковки нескольких единиц в одно место — это новая фича про «упаковщик», не входит в текущий скоуп.
