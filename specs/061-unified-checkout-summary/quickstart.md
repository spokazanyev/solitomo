# Quickstart — Unified Checkout Summary (061)

**Date**: 2026-05-27
**Plan**: [plan.md](./plan.md)

Цель — показать как локально проверить, что фича работает после реализации. Используется реализатором (Codex/live developer) и QA при manual smoke-тестах.

## Предусловия

- Локальный dev-сервер запущен: `pnpm --filter @soliton/web dev` (порт 3000).
- В локальной БД есть seeded каталог (`pnpm --filter @soliton/web seed:catalog`) — нужны товары для добавления в корзину.
- Активная ветка `061-unified-checkout-summary`.

## Шаг 2. Smoke-тест юр-формы (визуальный эталон)

1. Открыть `http://localhost:3000/cart/`.
2. Добавить 3–5 разных PDU из каталога в корзину.
3. Перейти на `http://localhost:3000/cart/checkout/invoice/`.
4. Посмотреть на правую sticky-колонку.

**Ожидаемый вид** (1-в-1 как на эталонном скрине из задачи):

```
ЗАКАЗ
─────────────────────────────────────────
Блок розеток 19″ 1U, S-4 IEC320…  4 800 ₽
S-4 IEC320C13 · 1 шт
Блок розеток 19″ 1U, S-4x2…       5 655 ₽
S-4x2 · 1 шт
─────────────────────────────────────────
Итого:                          10 455 ₽

☐ Я согласен с офертой и политикой…

[ 📜 Выписать счёт → ]

После создания заказа вы получите счёт по email.
Заказ начнёт движение после поступления оплаты.
```

**Что проверить**:
- Заголовок «ЗАКАЗ» (uppercase, серый).
- Все позиции с lineTotal.
- Под каждой — `{SKU} · {qty} шт`.
- Разделитель + «Итого: …» крупной цифрой.
- Чекбокс «Я согласен…» — единый стиль.
- Кнопка «Выписать счёт» с иконкой 📜 + стрелкой.
- Под кнопкой — текст про email-счёт.

## Шаг 5. Физ-форма — с выбранной доставкой курьером

1. Продолжаем шаг 4: вводим валидный адрес из DaData (например, «г Москва, Тверская 1»).
2. Дождаться расчёта доставки.
3. Выбрать СДЭК курьером.

**Ожидаемое изменение в правой колонке**:

```
─────────────────────────────────────────
Товары:                       X ₽
Доставка (СДЭК):              1 500 ₽
─────────────────────────────────────────
Итого к оплате:           (X+1500) ₽

☐ Я согласен с офертой и политикой…    ← если ещё не поставил

[ 💳 Перейти к оплате → ]  (enabled после consent)
```

**Что проверить**:
- Появилась строка «Доставка (СДЭК): 1 500 ₽» вместо подсказки.
- «Итого к оплате» = «Товары» + «Доставка» (арифметика верна).
- Поставить галочку → кнопка становится enabled.

## Шаг 10. Server validation — обходной submit

1. На checkout/physical/ заполнить корректно все поля **кроме** галочки consent.
2. Открыть DevTools → Console → выполнить:
   ```js
   document.querySelector('button[type="submit"]').removeAttribute('disabled');
   document.querySelector('form').requestSubmit();
   ```
3. **Ожидание**: сервер отвечает ошибкой (400 / consent required), форма не отправляется, заказ не создаётся.

Это проверка FR-019 — UI-блок disabled не единственный enforcement.

## Шаг 11. Аналитика (GA Debug View)

1. Включить **GA Debug Mode** в браузере: установить расширение «Google Analytics Debugger» (или префиксировать URL `?gtm_debug=true`).
2. Пройти полный flow физ-формы до клика «Перейти к оплате».
3. В Debug View убедиться что приходят события (в **той же последовательности** что до фичи):
   - `checkout_step_contact` (при первом фокусе в блок контактов)
   - `checkout_step_shipping` (при появлении валидного адреса)
   - `checkout_step_payment_method` (при mount формы с непустой корзиной)
   - `checkout_cta_pay_clicked` (нажатие кнопки)
   - `payment_intent` (после создания заказа)

То же для invoice flow — должны быть события `checkout_type: "legal"` + `inn_validation_success` / `inn_validation_failed` на blur ИНН.
