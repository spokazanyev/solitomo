# Feature Specification: Behavior & Ad Analytics

**Feature Branch**: `058-behavior-and-ad-analytics`

**Created**: 2026-05-25

**Status**: Draft

**Input**: На запуске сайта Soliton Organic есть MVP-разметка аналитики (загрузчик Метрики и GA4 с opt-in cookie-консентом из спеки 057; события `add_to_cart`, `begin_checkout`, `rfq_open`, `rfq_submit`, `view_item`, `view_cart`, `purchase`, `payment_intent`, `invoice_requested`), но её недостаточно, чтобы каждую неделю отвечать на бизнес-вопросы: где пользователи отваливаются по воронке, как они достигают целей, какие правки нужны на сайте и какая реклама окупается. Нужна сквозная разметка поведения, атрибуция рекламного трафика, серверные дубликаты ключевых событий, фильтрация ПДн и ботов, а также автоматизированный недельный отчёт. Яндекс.Метрика — основной инструмент; GA4 остаётся вторичным.

Версия 2 (после ревью senior-аналитика, 2026-05-25, Level B): добавлены нативный e-commerce-формат Метрики (отчёт «Электронная коммерция»), step-level воронка внутри checkout, отдельная регистрация `search_no_results`, архитектурная готовность к call-tracking, привязка `customer_id` к Метрика-UserID для кросс-устройственного анализа, аннотации релизов, JS-error/404/5xx tracking, когортный анализ и time-to-purchase, B2B-сигналы (price/stock visibility, ИНН-валидация, print/copy), обязательный набор ретаргетинговых сегментов, micro-goal `qualified_visit` для оптимизации Директа на холодных кампаниях, operator-guide для маркетолога.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Владелец видит, где люди отваливаются по воронке покупки (Priority: P1)

Каждый понедельник владелец сайта открывает Яндекс.Метрику и за 15 минут видит сводку: сколько уникальных пользователей прошли каждый шаг воронки `Главная/Лендинг → Каталог → Карточка товара → Корзина → Checkout → Оплата создана → Оплата успешна`, какой процент конверсии между шагами и где самый большой провал. Аналогично для воронок «RFQ», «Быстрый заказ» и «Скачивание документа».

**Why this priority**: Без полной воронки нельзя принимать решения о том, что чинить — это базовая основа недельного review. Без неё бизнес «летит вслепую» и тратит ресурсы на догадки.

**Independent Test**: Имитировать «happy path» (открыть лендинг → перейти в каталог → в карточку → добавить в корзину → checkout → оплата) в режиме инкогнито с принятым консентом. В Метрике в отчёте «Конверсии → Составные цели» виден count «1» на каждом шаге и нулевые провалы; повторить с прерыванием на checkout — виден drop-off на шаге «Оплата».

**Acceptance Scenarios**:

1. **Given** недельный отчёт в Метрике за полную неделю, **When** владелец открывает «Воронку покупки», **Then** видит шесть шагов с абсолютными и относительными цифрами и % drop-off между каждой парой шагов.
2. **Given** воронка RFQ, **When** владелец фильтрует по сегменту «не-боты», **Then** число шагов считается без AI-bot трафика.
3. **Given** пользователь добавил товар в корзину, но не дошёл до оплаты, **When** проверяется недельный отчёт, **Then** этот визит виден на шаге «Корзина» и отсутствует на шаге «Оплата».
4. **Given** пользователь скачал PDF документа на странице товара, **When** проверяется воронка «Документы», **Then** этот визит виден на шаге «Скачивание документа».

### User Story 2 — Владелец понимает, какая реклама окупается (Priority: P1)

Владелец запускает кампанию в Яндекс.Директе, размечает ссылки UTM-параметрами. Через неделю он открывает отчёт «Источники → Метки» в Метрике и видит, какие `utm_source/medium/campaign/content/term` принесли визиты, RFQ, заказы и выручку. Когда заказ из этой кампании оплачивается, в Метрику автоматически уходит «офлайн-конверсия» с привязкой к исходному клику (`yclid`), и Директ показывает её в отчётах для оптимизации ставок.

**Why this priority**: Без атрибуции невозможно оценить ROI рекламы; деньги тратятся «в темноту». На запуске рекламы это критично.

**Independent Test**: Открыть сайт по тестовой ссылке `?utm_source=test&utm_campaign=launch&yclid=TESTCLICK123`, добавить товар, оплатить тестовым платежом. В Order сохранены `utm_*` и `yclid`. В Метрике в «Источниках» виден визит с этими метками; в отчёте «Директ» (через 24 ч) виден yclid с привязкой к конверсии.

**Acceptance Scenarios**:

1. **Given** пользователь пришёл по ссылке с `?utm_source=yandex&utm_medium=cpc&utm_campaign=pdu-promo&yclid=ABC123`, **When** он добавляет товар и оформляет заказ, **Then** в записи заказа сохранены все UTM-параметры и `yclid` (и переносятся туда с этапа корзины).
2. **Given** заказ переходит в статус «оплачен», **When** срабатывает серверный хук офлайн-конверсии, **Then** в Метрике через её API регистрируется офлайн-конверсия с этим `yclid` и суммой заказа.
3. **Given** недельный отчёт по источникам, **When** владелец сортирует по выручке, **Then** видит топ-кампаний с числом заказов, средним чеком и стоимостью клика (если задана).
4. **Given** пользователь зашёл из органики (`utm_source` пустой), **When** проверяется визит, **Then** Метрика классифицирует источник как «Поисковые системы», а в Order сохраняется фактический referrer.

### User Story 3 — Микро-конверсии и поведение видны на уровне страниц (Priority: P2)

Маркетолог открывает отчёт «Карта кликов» и «Webvisor» для топ-10 страниц с высоким bounce, видит, как пользователи реально взаимодействуют со страницей: куда кликают, до какого блока скроллят, нажимают ли «Запросить КП» или «Скачать PDF». На страницах с низкой `scroll_depth_75` сразу понятно, что контент слабый или плохо сверстан.

**Why this priority**: Помогает находить конкретные UX-проблемы, но не блокирует ни запуск, ни первичное измерение воронки. P1-данные уже отвечают на «где проседаем», P2 — на «почему».

**Independent Test**: Открыть страницу товара, скроллить до 50%, кликнуть «Скачать PDF», вернуться. В Метрике в Webvisor видно запись визита; в «Карте кликов» виден клик по кнопке «Скачать PDF»; в событиях визита есть `scroll_depth_50` и `document_download`.

**Acceptance Scenarios**:

1. **Given** пользователь скроллит страницу до 25/50/75/100%, **When** проверяется визит в Метрике, **Then** каждый порог зафиксирован как отдельное событие ровно один раз.
2. **Given** пользователь нажимает на номер телефона в шапке, **When** проверяется событие, **Then** Метрика фиксирует цель «Клик по телефону» с источником-страницей.
3. **Given** пользователь применил фильтр в каталоге, **When** проверяется событие, **Then** Метрика фиксирует `filter_apply` с именем фильтра и категорией, без значения если оно идентифицирует пользователя.
4. **Given** пользователь ввёл запрос в строке поиска, **When** просматривается отчёт, **Then** виден сам запрос и число найденных позиций.

### User Story 4 — Конверсии не теряются у пользователей с adblock (Priority: P2)

B2B-байер с корпоративным ноутбуком и включённым блокировщиком оформляет заказ. Клиентские теги Метрики у него заблокированы, но заказ всё равно засчитывается в Метрике благодаря серверному хиту, отправленному с бэкенда после успешного webhook ЮKassa. Дубликата с клиентским событием нет — за счёт `transaction_id`.

**Why this priority**: Целевой B2B-сегмент часто использует adblock и корпоративные firewall. Без серверной страховки воронка занижает реальные конверсии и реклама недополучает данные для оптимизации.

**Independent Test**: В браузере включить агрессивный adblock (uBlock Origin со списком EasyList + EasyPrivacy), пройти checkout с тестовой оплатой ЮKassa. В Метрике в течение 5 минут появляется событие `purchase` с тем же `transaction_id`, что и в Payload Order. Снять блокировку и повторить — события не дублируются (дедупликация по `transaction_id`).

**Acceptance Scenarios**:

1. **Given** пользователь успешно оплатил заказ, **When** webhook ЮKassa подтверждает оплату, **Then** сервер отправляет серверный хит `purchase` с `transaction_id`, равным номеру заказа.
2. **Given** клиент уже отправил клиентское событие `purchase`, **When** серверный хит приходит с тем же `transaction_id`, **Then** Метрика считает это одной конверсией, а не двумя.
3. **Given** пользователь отправил RFQ-запрос с заблокированными скриптами, **When** API получает запрос, **Then** отправляется серверный хит `rfq_submit`.
4. **Given** заказ оплачен пользователем без согласия на cookie-аналитику (зашёл и сразу оплатил без принятия баннера — крайний кейс), **When** заказ создаётся, **Then** серверный хит **не** отправляется, потому что согласие не было дано (приватность важнее метрики).

### User Story 5 — Каждый понедельник владелец получает готовый weekly-отчёт (Priority: P2)

В понедельник утром администратор открывает страницу `/admin/analytics-report` или запускает команду формирования отчёта. Через пару минут получает структурированный документ за прошедшую неделю: воронка с цифрами, top-10 страниц по конверсиям, top-10 источников, total RFQ/Orders/Revenue, доля ботов, недельная динамика по сравнению с предыдущей неделей. Отчёт сохраняется в репозиторий как исторический срез.

**Why this priority**: Уменьшает «трение» недельного review и фиксирует историю — но базовые ответы доступны напрямую в Метрике даже без отчёта. P2 — упрощение работы, не блокер.

**Independent Test**: Запустить формирование отчёта за прошлую полную неделю. Получить файл `06-reports/analytics/2026-WW.md` с обязательными секциями: воронка покупки, воронка RFQ, источники, ботометрика, изменение к прошлой неделе. Открыть две недели подряд — динамика рассчитывается.

**Acceptance Scenarios**:

1. **Given** команда формирования отчёта запущена с диапазоном «прошлая неделя», **When** API Метрики возвращает данные, **Then** в `06-reports/analytics/` создаётся файл за эту неделю с обязательными секциями.
2. **Given** отчёт за две недели подряд, **When** владелец смотрит секцию «Динамика», **Then** видит изменение в процентах по каждому ключевому показателю.
3. **Given** API Метрики недоступен, **When** команда формирования отчёта запущена, **Then** возвращается понятная ошибка, файл не пишется частично.

### User Story 7 — Длинный цикл B2B: когорты, retention и время до покупки (Priority: P3)

Через 4-8 недель после запуска владелец заходит в недельный отчёт и видит когортную таблицу: сколько новых посетителей пришло в каждую неделю, какой % из них вернулся через 7/14/30/60 дней, какая доля в итоге купила. Параллельно — среднее и медианное «время до покупки» (от первого визита до оплаты) и среднее число визитов до конверсии. Это закрывает специфику B2B-цикла, где между «первым касанием» и «оплатой» обычно проходит 1-6 недель.

**Why this priority**: На запуске данных для retention ещё нет (нужен накопленный период), но без разметки сейчас — данные не накопятся. Поэтому событие/параметр должны быть готовы в v1, а сам отчёт — после первой полной недели.

**Independent Test**: На тестовых пользователях имитировать «двухвизитную» конверсию: открыть сайт в режиме инкогнито, закрыть; через 5 минут открыть в том же браузере (cookie сохраняется), оформить заказ. В записи заказа сохранены `first_seen_at`, `visit_count_to_purchase=2` и положительное `time_to_purchase_days`.

**Acceptance Scenarios**:

1. **Given** пользователь впервые зашёл на сайт, **When** создаётся новая сессия, **Then** в cookie фиксируется `first_seen_at`; при последующих визитах cookie не перезаписывается.
2. **Given** заказ оплачен, **When** срабатывает запись конверсии, **Then** в Order сохраняются `first_seen_at`, `time_to_purchase_days`, `visit_count_to_purchase`.
3. **Given** недельный отчёт через 4 недели после запуска, **When** владелец смотрит секцию «Когорты», **Then** видит retention rate по неделям D7/D14/D30 и медианное время до покупки.

### User Story 6 — Качество данных: ни ПДн в Метрике, ни мусора в воронке (Priority: P3)

Юрист и админ периодически проверяют, что в Метрике в записях Webvisor поля с email, телефоном, ФИО, ИНН и текстом ТЗ заштрихованы, а в параметрах событий нет ПДн. В фильтре «не-боты» воронка чистая — ClaudeBot/GPTBot/Yandex-AI и аналоги исключены.

**Why this priority**: Соответствие 152-ФЗ — обязательное условие для долгосрочной работы аналитики, но в первую неделю это можно проверить вручную, не блокируя запуск.

**Independent Test**: 1) Открыть форму checkout, ввести тестовый email, открыть DevTools → Network → запросы к `mc.yandex.ru/webvisor` — в payload email замаскирован; 2) Сделать в Webvisor запись и проверить визуально, что поля помечены маской; 3) В отчёте «Сегменты» применить «Исключить ботов» — счётчик визитов уменьшается; 4) Просмотреть payload любого события — ни в одном нет email/phone/ФИО/ИНН.

**Acceptance Scenarios**:

1. **Given** пользователь ввёл данные в форму, **When** записывается Webvisor, **Then** поля с ПДн (email, phone, ФИО, ИНН, текст комментария) заштрихованы.
2. **Given** AI-bot заходит на сайт, **When** идёт визит, **Then** в Метрике он помечен параметром «тип посетителя = бот» и может быть исключён сегментом.
3. **Given** любое событие из списка функциональных требований, **When** проверяется payload, **Then** в нём нет ни email, ни телефона, ни ФИО, ни ИНН, ни текста заявки.

### Edge Cases

- **Пользователь не дал согласие на cookie** — Метрика и GA4 не инициализируются; никакие клиентские события не отправляются; серверные дубликаты также не отправляются. На таких пользователях аналитики нет — это сознательная цена приватности.
- **Согласие дано в середине сессии** — после согласия инициализация происходит, события до этого момента теряются (это допустимое поведение и не противоречит закону).
- **Пользователь чистит cookie между визитами** — Метрика считает его новым визитёром; `client_id` меняется; атрибуция по `yclid` сохраняется только если он повторно перешёл по той же ссылке.
- **Один и тот же товар добавлен в корзину дважды** — событие `add_to_cart` отправляется дважды с указанием количества; `view_item` отправляется один раз на просмотр.
- **Пользователь оплачивает заказ дважды (повторная попытка после неудачи)** — отправляется `payment_retry`, а `purchase` — только один раз, когда платёж успешно завершён, по тому `transaction_id`, что и заказ.
- **Время между кликом по рекламе и оплатой больше 90 дней** — Метрика по умолчанию атрибутирует с окном 90 дней; более старые конверсии теряют связку с `yclid` — это особенность платформы, не баг.
- **Пользователь зашёл с одного UTM, потом ещё раз без UTM и оплатил** — последняя ненулевая метка считается источником; ранние UTM в Order не перезаписываются (first-touch для Order, last-touch для Метрики — обычное поведение).
- **Пользователь использует мобильное приложение почты (`?email=...` в ссылке-magic-link)** — `?email` не относится к UTM-whitelist и игнорируется атрибуцией; ничто не ломается.
- **Webvisor превысил лимит места** — Метрика сама ротирует записи; на сайте никаких действий не требуется.
- **Скрипт еженедельного отчёта запущен в воскресенье в 23:55, а в API Метрики ещё нет полных данных** — оператор получает предупреждение «данные за неделю могут быть неполными»; рекомендованное окно — понедельник после 10:00 по МСК.
- **Браузер не поддерживает Intersection Observer / Page Visibility API** — события `scroll_depth_*` и `view_item_list` (impressions) делают graceful fallback на простые `scroll`-listener'ы или вовсе пропускаются; конверсии и ecommerce-события при этом продолжают работать.
- **Аннотация деплоя создаётся локально в dev** — фильтруется по окружению (только prod-деплои попадают в weekly report); локальные сборки никогда не пишут аннотацию.
- **Customer-merge (слияние двух аккаунтов в один)** — старый Метрика-UserID не пересоздаётся, новые визиты привязаны к новому `customer_id`; ретроспективная склейка визитов не выполняется (это особенность Метрики).
- **Пользователь нажимает «Запросить цену» вместо «Купить»** — событие `price_request_click` отправляется, а `add_to_cart` нет; этот пользователь идёт по воронке RFQ, а не «Покупка».
- **Webvisor превысил лимит ёмкости из-за высокого трафика** — Метрика автоматически прореживает запись; владелец видит только часть сессий (обычно достаточно для CRO).
- **Печать страницы / копирование SKU в режиме инкогнито** — события `print_page` и `copy_text` идут, как обычно (приватность не влияет на агрегацию, в payload нет ПДн).

## Requirements *(mandatory)*

### Functional Requirements — Разметка событий

- **FR-001**: Система MUST отправлять событие `category_view` при просмотре страницы категории с параметрами `category_slug`, `items_count`, `page_type=category`.
- **FR-002**: Система MUST отправлять событие `view_item_list` при просмотре листинга (главная, каталог, категория, поиск) с массивом просматриваемых позиций и идентификатором списка.
- **FR-003**: Система MUST отправлять событие `select_item` при клике пользователя по карточке товара из листинга с позицией в списке и идентификатором списка.
- **FR-004**: Система MUST отправлять событие `search` при поиске по сайту с параметрами `search_term` и `results_count`.
- **FR-005**: Система MUST отправлять событие `filter_apply` при применении фильтра в каталоге с параметрами `filter_name`, `filter_value` (только нечувствительные значения) и `category_slug`.
- **FR-006**: Система MUST отправлять событие `document_download` при скачивании PDF (документация, паспорт, сертификат) с параметрами `document_type`, `filename` и (если применимо) `sku`.
- **FR-007**: Система MUST отправлять события `phone_click` и `email_click` при кликах на телефонные и email-ссылки в шапке, подвале и контактных блоках.
- **FR-008**: Система MUST отправлять события `scroll_depth_25`, `scroll_depth_50`, `scroll_depth_75`, `scroll_depth_100` ровно один раз за визит-на-странице с параметром `page_type`.
- **FR-009**: Система MUST отправлять событие `outbound_click` при кликах на внешние домены, чтобы такие визиты не считались отказами.
- **FR-010**: Система MUST отправлять событие `remove_from_cart` при удалении позиции из корзины с параметрами товара.
- **FR-011**: Система MUST отправлять событие `add_payment_info` при выборе пользователем способа оплаты на checkout.
- **FR-012**: Система MUST отправлять событие `add_shipping_info` при выборе пользователем способа доставки на checkout.
- **FR-013**: Система MUST отправлять события `view_promotion` и `select_promotion` для главных баннеров главной/категории с идентификатором баннера и позицией.
- **FR-014**: Система MUST отправлять события `quick_order_submit`, `company_form_submit`, `invoice_request_submit`, `callback_request_submit`, `file_upload` при соответствующих действиях в формах.
- **FR-015**: Система MUST отправлять событие `form_field_error` при провале валидации поля с идентификатором поля и кодом ошибки (без значения, введённого пользователем).
- **FR-016**: Система MUST отправлять события `payment_failed` (с параметром `reason`: `expired`, `cancelled_by_user`, `payment_method_declined`, `webhook_timeout`) и `payment_retry` при повторной попытке оплаты.
- **FR-017**: Система MUST отправлять события `shipment_rate_requested` и `shipment_selected` при работе с калькулятором доставки.
- **FR-018**: Система MUST отправлять событие `print_page` при печати страницы (через слушатель `beforeprint` / `window.matchMedia('print')`) с параметрами `page_type` и (если применимо) `sku`.
- **FR-019**: Система MUST отправлять событие `copy_text` при копировании пользователем «отслеживаемых» строк (артикул, SKU, ИНН, номер счёта, номер заказа — определяются атрибутом `data-trackable-copy="..."`) — с типом скопированного значения, без самого значения.

### Functional Requirements — Параметры событий и просмотров

- **FR-020**: Каждое событие просмотра MUST содержать параметр `page_type` со значением из закрытого списка: `home`, `catalog`, `category`, `pdp`, `knowledge`, `b2b`, `checkout`, `account`, `info`, `cart`, `success`, `other`.
- **FR-021**: События на SEO-кластерных страницах MUST содержать параметр `cluster` с идентификатором кластера, если он определён.
- **FR-022**: Каждое событие MUST содержать параметр `user_type` со значением из закрытого списка: `anonymous`, `customer`, `legal_entity`.
- **FR-023**: Первое событие сессии MUST содержать параметр `session_started_via` с источником входа (метка `utm_source` / тип реферера).
- **FR-024**: События PDP MUST содержать `sku` и `category_slug` товара.

### Functional Requirements — Атрибуция и UTM

- **FR-030**: Система MUST принимать и сохранять в cookie со сроком жизни 365 дней следующие метки из URL: `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `yclid`, `gclid`, `_openstat`, `from`. Все остальные параметры запроса игнорируются как метки атрибуции.
- **FR-031**: Корзина MUST хранить метки первого касания (first-touch) — устанавливаются при создании корзины и не перезаписываются.
- **FR-032**: При конверсии корзины в заказ метки атрибуции MUST копироваться в заказ (Order) без изменений.
- **FR-033**: При изменении статуса заказа на «оплачен» система MUST автоматически отправлять офлайн-конверсию в Яндекс.Метрику с привязкой к сохранённому `yclid` (если он есть) и сумме заказа.
- **FR-034**: При отсутствии `yclid` система MUST отправлять офлайн-конверсию с `client_id` Метрики (если он был сохранён в момент конверсии).
- **FR-035**: Cтраницы лендингов и продукта MUST корректно обрабатывать ссылки с параметрами атрибуции и не разрушать SEO-канонические URL (`?utm_*` исключены из канонической версии).

### Functional Requirements — Серверные события и устойчивость

- **FR-040**: Система MUST отправлять серверный хит `purchase` из бэкенда после подтверждённого webhook успешной оплаты — с тем же `transaction_id`, что используется в клиентском событии (равен номеру заказа), чтобы избежать дублирования.
- **FR-041**: Система MUST отправлять серверный хит `rfq_submit` из бэкенда при успешном приёме RFQ-запроса.
- **FR-042**: Серверные хиты MUST содержать `client_id` Метрики, если он был передан с клиента в момент конверсии; иначе использовать стабильный заместитель на базе сессии.
- **FR-043**: Серверные хиты MUST НЕ отправляться, если у пользователя нет согласия на аналитику-cookie на момент конверсии (если согласие было дано при checkout, оно считается достаточным для всей конверсии).
- **FR-044**: Сбой отправки серверного хита MUST НЕ приводить к сбою основной операции (оформление заказа/RFQ); ошибка только логируется.

### Functional Requirements — Цели Метрики и воронки

- **FR-050**: В Яндекс.Метрике MUST быть настроены цели на следующие события (через UI Метрики, ID хранятся в админ-настройках сайта): `rfq_submit`, `add_to_cart`, `begin_checkout`, `purchase`, `quick_order_submit`, `invoice_request_submit`, `document_download`, `phone_click`, `email_click`, `callback_request_submit`, `filter_apply`, `search`, `qualified_visit` (micro-goal, см. FR-210), `price_request_click` (см. FR-190).
- **FR-051**: В Метрике MUST быть настроены составные цели (воронки): **«Покупка детально»** (Главная/Лендинг → PDP → `add_to_cart` → `begin_checkout` → `checkout_step_contact` → `checkout_step_shipping` → `checkout_step_payment_method` → `checkout_step_review` → `checkout_cta_pay_clicked` → `payment_intent` → `purchase`); «RFQ» (PDP → `add_to_cart` → `rfq_open` → `rfq_submit`); «Быстрый заказ» (Каталог → `quick_order_submit`); «Документы» (PDP → `document_download`); «B2B запрос цены» (PDP → `price_request_click` → `rfq_submit` или `callback_request_submit`).
- **FR-052**: Главная цель «Покупка» MUST быть основной целью счётчика для Директа (используется при оптимизации ставок). Цель `qualified_visit` MUST быть прописана как micro-conversion для оптимизации Директа на холодных кампаниях, где конверсий в `purchase` ещё мало.

### Functional Requirements — Webvisor, тепловые карты, приватность

- **FR-060**: Поля с ПДн (email, телефон, ФИО, ИНН, текст комментария / описания / ТЗ) MUST быть помечены так, чтобы их содержимое не передавалось в Webvisor и не записывалось в его архив. Это касается всех форм сайта: RFQ, checkout (физ/юр), быстрый заказ, callback, регистрация, восстановление пароля.
- **FR-061**: Webvisor MUST оставаться активным для нечувствительных частей страниц (карточки, кнопки, навигация).
- **FR-062**: Параметры всех событий MUST НЕ содержать значений ПДн (email, телефон, ФИО, ИНН, текст комментария).
- **FR-063**: Тепловые карты и карты ссылок MUST быть включены.

### Functional Requirements — Web Vitals и качество страниц

- **FR-070**: Система MUST измерять и отправлять в Метрику показатели Web Vitals — LCP (Largest Contentful Paint), CLS (Cumulative Layout Shift), INP (Interaction to Next Paint) — как параметры визита или первого page-view.
- **FR-071**: Показатели Web Vitals MUST быть видны в Метрике с разбивкой по типу страницы (`page_type`), чтобы можно было определить, какие шаблоны страниц медленные.

### Functional Requirements — Боты и качество трафика

- **FR-080**: Каждое событие/визит MUST содержать параметр `visitor_type` со значением `human` или `bot`. Классификация выполняется по User-Agent и набору известных шаблонов AI-bot / поисковых ботов, конфигурируемому через настройки админ-панели.
- **FR-081**: В Метрике MUST быть сохранён сегмент «Исключить ботов» для использования во всех ключевых отчётах и воронках.

### Functional Requirements — Недельный отчёт

- **FR-090**: Система MUST предоставлять способ автоматически сформировать отчёт за выбранный недельный диапазон (понедельник—воскресенье).
- **FR-091**: Отчёт MUST включать секции: «Воронка покупки детальная» (с шагами checkout + drop-off), «Воронка RFQ», «Источники» (по `utm_source`/`utm_medium`/`utm_campaign`), «Топ-10 landing-pages по конверсиям», «Топ-10 query-clusters по конверсиям» (если данные доступны), «Внутренний поиск: топ-запросы и топ-без-результата», «Total RFQ/Orders/Revenue», «Электронная коммерция: топ-5 товаров, средний чек, выручка по категориям», «Качество визита: доля `qualified_visit`», «B2B-сигналы: `price_request_click`, `inn_validation_failed`», «Когорты и retention: D7/D30, медианное `time_to_purchase`», «Доля ботов и JS-ошибок», «Аннотации релизов/инцидентов недели», «Динамика к предыдущей неделе» (% по ключевым показателям).
- **FR-092**: Отчёт MUST сохраняться как версионируемый текстовый артефакт в репозиторий по пути `06-reports/analytics/YYYY-WW.md` с понятным шаблоном.
- **FR-093**: При недоступности API Метрики команда формирования MUST возвращать понятную ошибку и НЕ создавать частичный файл отчёта.

### Functional Requirements — Конфигурация и эксплуатация

- **FR-100**: Идентификаторы счётчика Метрики, GA4, токен API Метрики и список целей MUST храниться в безопасном хранилище конфигурации (env / Payload Globals в зашифрованном поле); никогда не коммитятся в git.
- **FR-101**: В админ-панели MUST быть единая страница «Аналитика»: статус подключений (Метрика/GA4/API), список настроенных целей, список ботовых шаблонов, ссылка на последний отчёт.
- **FR-102**: Изменение настроек аналитики MUST логироваться в audit log админки.

### Key Entities

- **AnalyticsEvent** — событие, отправляемое в Метрику и/или GA4. Атрибуты: имя события, параметры события (без ПДн), `transaction_id` для конверсионных событий, `page_type`, `user_type`, метка времени, идентификатор клиента Метрики, серверный/клиентский источник.
- **AttributionTouchpoint** — точка касания пользователя с рекламой/источником. Атрибуты: набор UTM-меток, `yclid`/`gclid`, реферер, время первого касания, признак first-touch/last-touch.
- **OfflineConversion** — событие конверсии, отправленное в Метрику с сервера после изменения статуса заказа. Атрибуты: тип конверсии (`purchase`), `transaction_id` (= номер заказа), сумма, валюта, `yclid`/`client_id`, признак, был ли продублирован клиент-side.
- **WeeklyReport** — артефакт отчёта за неделю. Атрибуты: период (week/year), секции (воронки, источники, ботометрика, динамика), путь сохранения, дата генерации.
- **AnalyticsSettings** — конфигурация системы. Атрибуты: идентификаторы счётчиков, список целей, ботовые шаблоны, признак активации серверных хитов, признак активации Webvisor.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На основной user journey (Главная → PDP → Добавление в корзину → Checkout → Успешная оплата) в Яндекс.Метрике в течение 30 минут после действия видна полная воронка с количеством на каждом шаге; drop-off rate можно вычислить.
- **SC-002**: Все события из FR-001…FR-017 видны в режиме отладки Метрики на тестовой сессии «happy path»; ни одно ключевое событие не пропущено.
- **SC-003**: Владелец может за 30 минут получить готовый недельный отчёт (запуск инструмента + просмотр отчётов Метрики) и принять минимум одно решение «что чинить на сайте» по конкретным данным.
- **SC-004**: При покупке через ссылку с `?yclid=...` в записи заказа сохранены метки, а при переходе заказа в статус «оплачен» в Яндекс.Метрике в отчёте «Директ» в течение 24 часов появляется офлайн-конверсия с этим `yclid`.
- **SC-005**: Пользователь с активным adblock, прошедший оплату, виден в Метрике благодаря серверному хиту; повторный визит без adblock не создаёт дубль конверсии (дедупликация по `transaction_id` работает).
- **SC-006**: В выборочной проверке 10 случайных Webvisor-записей и payload-ов 20 случайных событий не найдено ни одного случая утечки email, телефона, ФИО, ИНН или текста комментария.
- **SC-007**: Показатели Web Vitals (LCP, CLS, INP) видны в Метрике в отчёте «Производительность» с разбивкой по типу страницы; известны 3 шаблона страниц с худшими значениями.
- **SC-008**: За первые две полные недели после запуска рекламы Метрика показывает не менее одного источника с измеримой конверсией (RFQ или заказ), а владелец может сравнить ROI разных кампаний.
- **SC-009**: При фильтре «не-боты» количество визитов уменьшается; владелец может видеть «чистую» воронку без AI-bot шума.
- **SC-010**: Историческая папка `06-reports/analytics/` после 4 недель работы содержит 4 файла, по одному на каждую полную неделю; динамика «неделя к неделе» рассчитывается автоматически.

## Assumptions

- **Согласие пользователя обязательно для аналитики.** Cookie-консент уже реализован в спеке 057; и клиентские, и серверные события отправляются только при наличии согласия (исключение — серверная страховка для уже paid-заказа, где согласие было дано в checkout).
- **Метрика — основной инструмент, GA4 — вторичный.** Серверные хиты, кастомные параметры, цели, воронки и отчёты делаются для Метрики. Тот же набор событий по возможности уходит и в GA4 (через тот же `dataLayer`), но без серверной части и без оптимизации под GA4.
- **Окно атрибуции — стандартное для Метрики (90 дней).** Любые конверсии вне этого окна теряют связку с кликом — это особенность платформы.
- **Атрибуция в Order — first-touch, в Метрике — last non-direct click.** Это сознательное расхождение: бизнесу важно знать «откуда пришёл пользователь изначально» (Order), а Метрика по умолчанию работает в last-touch модели.
- **AI-bot policy (отдельная спека 038) откладывается.** Эта спека лишь использует базовую детекцию ботов по User-Agent и параметр `visitor_type`; полная политика индексации и логирование AI-bot останутся в 038.
- **Twenty CRM пока выключен (спека 048).** Офлайн-конверсии из CRM («менеджер закрыл сделку») в v1 не реализуются; реализуется только офлайн-конверсия из изменения статуса заказа на «оплачен».
- **A/B-тестирование не входит в v1.** Это отдельная инициатива.
- **Метрика «Заказы» (ecommerce dashboard внутри Метрики через специальный синтаксис dataLayer)** в v1 не настраивается; используется стандартная разметка событий. Перевод на ecommerce-объект — отдельная задача.
- **Конфигурация рекламы и создание кампаний не входит в скоуп.** Эта спека готовит инфраструктуру измерения; запуск рекламы — самостоятельный процесс на стороне маркетинга.
- **Стандарт безопасности.** Токены API Метрики и идентификаторы счётчиков хранятся в env / зашифрованных полях; не коммитятся.

## Dependencies

- Спека 057 (`yookassa-buyer-info-compliance`) — opt-in cookie-консент и текущий загрузчик аналитики. Эта спека расширяет ту инфраструктуру.
- Спека 055/056 (`yookassa-payments-integration` + frontend) — события `purchase`, `payment_intent`, webhook-после-оплаты, `transaction_id`. Эта спека добавляет серверные дубликаты и расширенные `payment_failed`/`payment_retry`.
- Спека 052 (`cart-as-entity`) — поле атрибуции на корзине (first-touch UTM) и перенос в Order при конверсии.
- Спека 047 (`delivery-checkout-apiship`) — события доставки.
- Канонический документ `07-build-specifications/analytics-measurement-spec.md` — справочник, обновляется по итогам этой спеки.
