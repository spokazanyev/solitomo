# Feature Specification: Behavior & Ad Analytics

**Feature Branch**: `058-behavior-and-ad-analytics`

**Created**: 2026-05-25

**Status**: Draft

**Input**: На запуске сайта Soliton Organic есть MVP-разметка аналитики (загрузчик Метрики и GA4 с opt-in cookie-консентом из спеки 057; события `add_to_cart`, `begin_checkout`, `rfq_open`, `rfq_submit`, `view_item`, `view_cart`, `purchase`, `payment_intent`, `invoice_requested`), но её недостаточно, чтобы каждую неделю отвечать на бизнес-вопросы: где пользователи отваливаются по воронке, как они достигают целей, какие правки нужны на сайте и какая реклама окупается. Нужна сквозная разметка поведения, атрибуция рекламного трафика, серверные дубликаты ключевых событий, фильтрация ПДн и ботов, а также автоматизированный недельный отчёт. Яндекс.Метрика — основной инструмент; GA4 остаётся вторичным.

Версия 2 (после ревью senior-аналитика, 2026-05-25, Level B): добавлены нативный e-commerce-формат Метрики (отчёт «Электронная коммерция»), step-level воронка внутри checkout, отдельная регистрация `search_no_results`, архитектурная готовность к call-tracking, привязка `customer_id` к Метрика-UserID для кросс-устройственного анализа, аннотации релизов, JS-error/404/5xx tracking, когортный анализ и time-to-purchase, B2B-сигналы (price/stock visibility, ИНН-валидация, print/copy), обязательный набор ретаргетинговых сегментов, micro-goal `qualified_visit` для оптимизации Директа на холодных кампаниях, operator-guide для маркетолога.

Версия 3 (после ревью senior-аналитика + SEO, 2026-05-25, Level C-Full): закрыт «слепой» организический канал и базовая инженерная гигиена. Добавлены: интеграция Я.Вебмастера и Google Search Console в weekly-отчёт (запросы/показы/CTR/позиции/индекс/sitemap), пост-кликовая связка «запрос → URL → конверсия», классификация реферера (включая AI-поисковики, картинки, маркетплейсы, соц), brand-vs-non-brand split, мониторинг crawl-ошибок и Soft 404, индекс-санитар, per-кластер outlier-детекция, регистрация органических PDF-скачиваний, изоляция test/staging-счётчиков, мета-аналитика cookie-banner (accept/decline rate), pre-deploy smoke-test событий с блокировкой PR, goal-mapping artifact, автоимпорт стоимости Я.Директа и ROAS, retry-очередь для серверных хитов, базовое событие `page_view` для прочих страниц, webhook на достижение целей в admin-alerting, first-party cookies Метрики (ITP-resilience), runbook 152-ФЗ для аналитических данных.

## Clarifications

### Session 2026-05-25

- Q: Как система определяет `user_type=legal_entity`? → A: Гибрид — либо введён ИНН в любой форме (sticky cookie 365 дней), либо есть Company-связка в авторизованном Customer; whichever happens first wins.
- Q: В каком формате выдавать недельный отчёт? → A: MD-источник в `06-reports/analytics/YYYY-WW.md` (canonical, git-history) + HTML-rendering в Payload admin `/admin/analytics-report` (читает MD и отрисовывает с графиками динамики + кликабельными ссылками в Метрику). Дублирования данных нет: HTML рендерится из MD на лету.
- Q: Где хранить runtime-секреты внешних API (Webmaster OAuth, GSC service account, Метрика API token, Telegram bot token)? → A: Все секреты — в env-переменных (`.env` / production env), как у существующих интеграций (ЮKassa, ApiShip, CRON_SECRET). Ротация требует redeploy. Payload Globals остаются для **не-секретных** конфигураций (списки host-паттернов реферера, ботовые UA-шаблоны, Soft-404-маркеры, список целей, флаги активации) — их редактирует админ без redeploy.
- Q: Чем исполнять pre-deploy smoke-test событий? → A: Гибрид — jsdom (vitest) прогоняет 80% событий за секунды на каждом PR (event-helpers, структура `dataLayer`, отсутствие ПДн); Playwright прогоняет в реальном headless-браузере критичные конверсионные пути (PDP→cart→checkout-steps→purchase, RFQ-submit, scroll_depth через Intersection Observer, `beforeprint`) перед production-деплоем. Регрессия любого слоя блокирует CI.
- Q: Источник `first_seen_at` для когортного анализа? → A: Гибрид — cookie `_solitomo_first_seen` (TTL 365 дней) как primary для анонимов; для авторизованных Customer-ов значение хранится в поле `customer.firstSeenAt` (Payload) и используется как min(cookie, customer.firstSeenAt) для устойчивости к чистке cookie. При первом логине backend записывает min из существующих значений; при последующих визитах с того же `customer_id` используется backend-value, даже если cookie стёрто.

## Scope Phases (MVP-Lite Breakdown)

Спека описывает полную целевую разметку аналитики. Для launch — поэтапная реализация: **v1 (MVP-Lite)** — то, что нужно с первого дня, чтобы недельный отчёт отвечал на 4 главных вопроса бизнеса. **v1.1** — расширения, которые имеют смысл после первого месяца накопления данных. **v1.2** — функционал, который оправдан только при существенном трафике/каталоге.

Принципы фазировки:
1. Если Метрика/Вебмастер/GSC уже дают данные из коробки — кастомная разметка откладывается до момента, когда станет видна реальная потеря точности.
2. Если функционал требует трафика для осмысленности — откладывается до v1.1 (после первого месяца).
3. Если функционал зависит от продуктовой возможности, которой ещё нет (промо-баннеры, callback-форма, отдельный invoice-request) — событие откладывается вместе с продуктовой фичей.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Владелец видит, где люди отваливаются по воронке покупки (Priority: P1)

Каждый понедельник владелец сайта открывает Яндекс.Метрику и за 15 минут видит сводку: сколько уникальных пользователей прошли каждый шаг воронки `Главная/Лендинг → Каталог → Карточка товара → Корзина → Checkout → Оплата создана → Оплата успешна`, какой процент конверсии между шагами и где самый большой провал. Аналогично для воронок «RFQ», «Быстрый заказ» и «Скачивание документа».

**Why this priority**: Без полной воронки нельзя принимать решения о том, что чинить — это базовая основа недельного review. Без неё бизнес «летит вслепую» и тратит ресурсы на догадки.

**Independent Test**: Имитировать «happy path» (открыть лендинг → перейти в каталог → в карточку → добавить в корзину → checkout → оплата) в режиме инкогнито с принятым консентом. В Метрике в отчёте «Конверсии → Составные цели» виден count «1» на каждом шаге и нулевые провалы; повторить с прерыванием на checkout — виден drop-off на шаге «Оплата».

**Acceptance Scenarios**:

1. **Given** недельный отчёт в Метрике за полную неделю, **When** владелец открывает «Воронку покупки», **Then** видит шесть шагов с абсолютными и относительными цифрами и % drop-off между каждой парой шагов.
2. **Given** воронка RFQ, **When** владелец фильтрует по сегменту «не-боты», **Then** число шагов считается без AI-bot трафика.
3. **Given** пользователь добавил товар в корзину, но не дошёл до оплаты, **When** проверяется недельный отчёт, **Then** этот визит виден на шаге «Корзина» и отсутствует на шаге «Оплата».
4. **Given** пользователь скачал PDF документа на странице товара, **When** проверяется воронка «Документы», **Then** этот визит виден на шаге «Скачивание документа».

### User Story 2 — Владелец понимает, какая реклама окупается (Priority: P1)

Владелец запускает кампанию в Яндекс.Директе, размечает ссылки UTM-параметрами. Через неделю он открывает отчёт «Источники → Метки» в Метрике и видит, какие `utm_source/medium/campaign/content/term` принесли визиты, RFQ, заказы и выручку. Когда заказ из этой кампании оплачивается, в Метрику автоматически уходит «офлайн-конверсия» с привязкой к исходному клику (`yclid`), и Директ показывает её в отчётах для оптимизации ставок.

**Why this priority**: Без атрибуции невозможно оценить ROI рекламы; деньги тратятся «в темноту». На запуске рекламы это критично.

**Independent Test**: Открыть сайт по тестовой ссылке `?utm_source=test&utm_campaign=launch&yclid=TESTCLICK123`, добавить товар, оплатить тестовым платежом. В Order сохранены `utm_*` и `yclid`. В Метрике в «Источниках» виден визит с этими метками; в отчёте «Директ» (через 24 ч) виден yclid с привязкой к конверсии.

**Acceptance Scenarios**:

1. **Given** пользователь пришёл по ссылке с `?utm_source=yandex&utm_medium=cpc&utm_campaign=pdu-promo&yclid=ABC123`, **When** он добавляет товар и оформляет заказ, **Then** в записи заказа сохранены все UTM-параметры и `yclid` (и переносятся туда с этапа корзины).
2. **Given** заказ переходит в статус «оплачен», **When** срабатывает серверный хук офлайн-конверсии, **Then** в Метрике через её API регистрируется офлайн-конверсия с этим `yclid` и суммой заказа.
3. **Given** недельный отчёт по источникам, **When** владелец сортирует по выручке, **Then** видит топ-кампаний с числом заказов, средним чеком и стоимостью клика (если задана).
4. **Given** пользователь зашёл из органики (`utm_source` пустой), **When** проверяется визит, **Then** Метрика классифицирует источник как «Поисковые системы», а в Order сохраняется фактический referrer.

### User Story 8 — SEO-команда видит органический канал в едином недельном срезе (Priority: P1)

Каждый понедельник SEO-специалист открывает недельный отчёт и видит секцию «Организический канал»: какие поисковые запросы недели приносили показы и клики (отдельно brand vs non-brand), какие новые запросы появились и какие потеряны, какие landing-страницы выросли/упали, какой статус индекса в Я.Вебмастере и GSC, есть ли новые crawl-ошибки и Soft 404, какие страницы получили rich snippets/быстрый ответ. Для AI-поисковиков (Perplexity, ChatGPT, Claude, Алиса-нейро) виден отдельный канал.

**Why this priority**: Проект буквально называется `soliton-organic-site`; SEO — основной канал привлечения. Без этой секции weekly-отчёт описывает только платную часть и оставляет 70-80% трафика без аналитики.

**Independent Test**: Подключить тестовые токены Я.Вебмастера + GSC. Запустить формирование отчёта за прошлую полную неделю — секция «Организический канал» содержит топ-30 запросов, топ-10 landing pages, brand-долю, число страниц в индексе, статус sitemap, новые/потерянные запросы. На отдельных тестовых страницах с заранее размеченной schema.org — секция «Schema-org effectiveness» показывает их в числе страниц с rich snippets.

**Acceptance Scenarios**:

### User Story 4 — Конверсии не теряются у пользователей с adblock (Priority: P2)

B2B-байер с корпоративным ноутбуком и включённым блокировщиком оформляет заказ. Клиентские теги Метрики у него заблокированы, но заказ всё равно засчитывается в Метрике благодаря серверному хиту, отправленному с бэкенда после успешного webhook ЮKassa. Дубликата с клиентским событием нет — за счёт `transaction_id`.

**Why this priority**: Целевой B2B-сегмент часто использует adblock и корпоративные firewall. Без серверной страховки воронка занижает реальные конверсии и реклама недополучает данные для оптимизации.

**Independent Test**: В браузере включить агрессивный adblock (uBlock Origin со списком EasyList + EasyPrivacy), пройти checkout с тестовой оплатой ЮKassa. В Метрике в течение 5 минут появляется событие `purchase` с тем же `transaction_id`, что и в Payload Order. Снять блокировку и повторить — события не дублируются (дедупликация по `transaction_id`).

**Acceptance Scenarios**:

1. **Given** пользователь успешно оплатил заказ, **When** webhook ЮKassa подтверждает оплату, **Then** сервер отправляет серверный хит `purchase` с `transaction_id`, равным номеру заказа.
2. **Given** клиент уже отправил клиентское событие `purchase`, **When** серверный хит приходит с тем же `transaction_id`, **Then** Метрика считает это одной конверсией, а не двумя.
3. **Given** пользователь отправил RFQ-запрос с заблокированными скриптами, **When** API получает запрос, **Then** отправляется серверный хит `rfq_submit`.
4. **Given** заказ оплачен пользователем без согласия на cookie-аналитику (зашёл и сразу оплатил без принятия баннера — крайний кейс), **When** заказ создаётся, **Then** серверный хит **не** отправляется, потому что согласие не было дано (приватность важнее метрики).

### User Story 7 — Длинный цикл B2B: когорты, retention и время до покупки (Priority: P3)

Через 4-8 недель после запуска владелец заходит в недельный отчёт и видит когортную таблицу: сколько новых посетителей пришло в каждую неделю, какой % из них вернулся через 7/14/30/60 дней, какая доля в итоге купила. **Why this priority**: На запуске данных для retention ещё нет (нужен накопленный период), но без разметки сейчас — данные не накопятся. Поэтому событие/параметр должны быть готовы в v1, а сам отчёт — после первой полной недели.

**Independent Test**: На тестовых пользователях имитировать «двухвизитную» конверсию: открыть сайт в режиме инкогнито, закрыть; через 5 минут открыть в том же браузере (cookie сохраняется), оформить заказ. **Acceptance Scenarios**:

2. **Given** заказ оплачен, **When** срабатывает запись конверсии, **Then** в Order сохраняются `first_seen_at`, `time_to_purchase_days`, `visit_count_to_purchase`.
3. **Given** недельный отчёт через 4 недели после запуска, **When** владелец смотрит секцию «Когорты», **Then** видит retention rate по неделям D7/D14/D30 и медианное время до покупки.

### Edge Cases

- **Пользователь не дал согласие на cookie** — Метрика и GA4 не инициализируются; никакие клиентские события не отправляются; серверные дубликаты также не отправляются. На таких пользователях аналитики нет — это сознательная цена приватности.
- **Согласие дано в середине сессии** — после согласия инициализация происходит, события до этого момента теряются (это допустимое поведение и не противоречит закону).
- **Пользователь чистит cookie между визитами** — Метрика считает его новым визитёром; `client_id` меняется; атрибуция по `yclid` сохраняется только если он повторно перешёл по той же ссылке.
- **Один и тот же товар добавлен в корзину дважды** — событие `add_to_cart` отправляется дважды с указанием количества; `view_item` отправляется один раз на просмотр.
- **Пользователь оплачивает заказ дважды (повторная попытка после неудачи)** — отправляется `payment_retry`, а `purchase` — только один раз, когда платёж успешно завершён, по тому `transaction_id`, что и заказ.
- **Время между кликом по рекламе и оплатой больше 90 дней** — Метрика по умолчанию атрибутирует с окном 90 дней; более старые конверсии теряют связку с `yclid` — это особенность платформы, не баг.
- **Пользователь зашёл с одного UTM, потом ещё раз без UTM и оплатил** — последняя ненулевая метка считается источником; ранние UTM в Order не перезаписываются (first-touch для Order, last-touch для Метрики — обычное поведение).
- **Пользователь использует мобильное приложение почты (`?email=...` в ссылке-magic-link)** — `?email` не относится к UTM-whitelist и игнорируется атрибуцией; ничто не ломается.
- **Webvisor превысил лимит места** — Метрика сама ротирует записи; на сайте никаких действий не требуется.
- **Скрипт еженедельного отчёта запущен в воскресенье в 23:55, а в API Метрики ещё нет полных данных** — оператор получает предупреждение «данные за неделю могут быть неполными»; рекомендованное окно — понедельник после 10:00 по МСК.
- **Браузер не поддерживает Intersection Observer / Page Visibility API** — события `scroll_depth_*` и `view_item_list` (impressions) делают graceful fallback на простые `scroll`-listener'ы или вовсе пропускаются; конверсии и ecommerce-события при этом продолжают работать.
- **Аннотация деплоя создаётся локально в dev** — фильтруется по окружению (только prod-деплои попадают в weekly report); локальные сборки никогда не пишут аннотацию.
- **Customer-merge (слияние двух аккаунтов в один)** — старый Метрика-UserID не пересоздаётся, новые визиты привязаны к новому `customer_id`; ретроспективная склейка визитов не выполняется (это особенность Метрики).
- **Пользователь нажимает «Запросить цену» вместо «Купить»** — событие `price_request_click` отправляется, а `add_to_cart` нет; этот пользователь идёт по воронке RFQ, а не «Покупка».
- **Webvisor превысил лимит ёмкости из-за высокого трафика** — Метрика автоматически прореживает запись; владелец видит только часть сессий (обычно достаточно для CRO).
- **Печать страницы / копирование SKU в режиме инкогнито** — события `print_page` и `copy_text` идут, как обычно (приватность не влияет на агрегацию, в payload нет ПДн).
- **Я.Вебмастер не подтверждён владельцем домена** — секция «Я.Вебмастер» пуста с пометкой «домен не подтверждён, действие: подтвердить через UI Вебмастера».
- **GSC квота API исчерпана** — формирование отчёта использует кеш предыдущей выгрузки; на странице отчёта помечается «данные из кеша от DATE».
- **AI-поисковик присылает визит без узнаваемого User-Agent / реферера** — попадает в категорию `referral` или `direct`; это допустимая утечка; добавление нового AI-агента — через конфигурацию (FR-241), без релиза.
- **Production-счётчик случайно подключился в staging-сборке** — суточная проверка (FR-272) видит визиты с `env=staging` и алертит; production-данные за этот период помечаются как «возможно загрязнены».
- **Cookie-banner показан, но пользователь закрыл вкладку до выбора** — событие `consent_banner_shown` сохраняется в cookie и уходит при следующем визите (если консент тогда будет дан); если пользователь больше не вернётся — событие не уходит, считается как «no-action».
- **Серверный хит провалился все 5 retry-попыток** — заказ при этом давно создан и пользователь получил подтверждение; в Метрике конверсия отсутствует, но в admin-alerting есть запись «hit failed for transaction_id=X», админ может вручную поправить через API Метрики.
- **Я.Метрика-счётчик не связан с Я.Директ-аккаунтом** — секция «Эффективность Директа» в отчёте явно содержит пометку «не подключено», а не молчаливо пустая.
- **Safari/iOS с активным ITP, домен счётчика на CNAME настроен некорректно** — first-party cookies не работают, пользователь определяется как «новый» каждый раз; в weekly-отчёте видна аномалия «доля новых посетителей в Safari >> чем в Chrome», что и есть симптом — админ проверяет DNS.
- **PDF-документ отдаётся напрямую из выдачи (без HTML-обёртки)** — клиентский tracker не сработает; либо серверный хит, либо промежуточный landing — иначе скачивание невидимо.

## Requirements *(mandatory)*

### Functional Requirements — Разметка событий

- **FR-001**: Система MUST отправлять событие `category_view` при просмотре страницы категории с параметрами `category_slug`, `items_count`, `page_type=category`.
- **FR-002**: Система MUST отправлять событие `view_item_list` при просмотре листинга (главная, каталог, категория, поиск) с массивом просматриваемых позиций и идентификатором списка.
- **FR-003**: Система MUST отправлять событие `select_item` при клике пользователя по карточке товара из листинга с позицией в списке и идентификатором списка.
- **FR-004**: Система MUST отправлять событие `search` при поиске по сайту с параметрами `search_term` и `results_count`.
- **FR-005**: Система MUST отправлять событие `filter_apply` при применении фильтра в каталоге с параметрами `filter_name`, `filter_value` (только нечувствительные значения) и `category_slug`.
- **FR-006**: Система MUST отправлять событие `document_download` при скачивании PDF (документация, паспорт, сертификат) с параметрами `document_type`, `filename` и (если применимо) `sku`.
- **FR-007**: Система MUST отправлять события `phone_click` и `email_click` при кликах на телефонные и email-ссылки в шапке, подвале и контактных блоках.
- **FR-008**: Система MUST отправлять события `scroll_depth_25`, `scroll_depth_50`, `scroll_depth_75`, `scroll_depth_100` ровно один раз за визит-на-странице с параметром `page_type`.
- **FR-009**: Система MUST отправлять событие `outbound_click` при кликах на внешние домены, чтобы такие визиты не считались отказами.
- **FR-010**: Система MUST отправлять событие `remove_from_cart` при удалении позиции из корзины с параметрами товара.
- **FR-011**: Система MUST отправлять событие `add_payment_info` при выборе пользователем способа оплаты на checkout.
- **FR-012**: Система MUST отправлять событие `add_shipping_info` при выборе пользователем способа доставки на checkout.
- **FR-013**: Система MUST отправлять события `view_promotion` и `select_promotion` для главных баннеров главной/категории с идентификатором баннера и позицией.
- **FR-014**: Система MUST отправлять события `quick_order_submit`, `company_form_submit`, `invoice_request_submit`, `callback_request_submit`, `file_upload` при соответствующих действиях в формах.
- **FR-015**: Система MUST отправлять событие `form_field_error` при провале валидации поля с идентификатором поля и кодом ошибки (без значения, введённого пользователем).
- **FR-016**: Система MUST отправлять события `payment_failed` (с параметром `reason`: `expired`, `cancelled_by_user`, `payment_method_declined`, `webhook_timeout`) и `payment_retry` при повторной попытке оплаты.
- **FR-017**: Система MUST отправлять события `shipment_rate_requested` и `shipment_selected` при работе с калькулятором доставки.
- **FR-018**: Система MUST отправлять событие `print_page` при печати страницы (через слушатель `beforeprint` / `window.matchMedia('print')`) с параметрами `page_type` и (если применимо) `sku`.
- **FR-019**: Система MUST отправлять событие `copy_text` при копировании пользователем «отслеживаемых» строк (артикул, SKU, ИНН, номер счёта, номер заказа — определяются атрибутом `data-trackable-copy="..."`) — с типом скопированного значения, без самого значения.

### Functional Requirements — Параметры событий и просмотров

- **FR-020**: Каждое событие просмотра MUST содержать параметр `page_type` со значением из закрытого списка: `home`, `catalog`, `category`, `pdp`, `knowledge`, `b2b`, `checkout`, `account`, `info`, `cart`, `success`, `other`.
- **FR-021**: События на SEO-кластерных страницах MUST содержать параметр `cluster` с идентификатором кластера, если он определён.
- **FR-022**: Каждое событие MUST содержать параметр `user_type` со значением из закрытого списка: `anonymous`, `customer`, `legal_entity`. Классификация по гибридному правилу: значение становится `legal_entity` при наступлении **первого из** двух условий — (a) пользователь впервые вводит ИНН в любой форме сайта (RFQ, checkout-юрлицо, callback, invoice, регистрация компании), факт фиксируется в sticky-cookie с TTL 365 дней; (b) пользователь авторизован и его Customer-запись связана с Company-сущностью (спека 054). Whichever happens first wins. Sticky-флаг **не сбрасывается** при выходе из аккаунта и **не понижается** до `customer`/`anonymous`, пока не истечёт cookie или пользователь явно не запросит «забыть меня» (152-ФЗ DSAR, FR-351). До первого срабатывания одного из условий значение — `customer` (для авторизованных без Company) или `anonymous`.
- **FR-023**: Первое событие сессии MUST содержать параметр `session_started_via` с источником входа (метка `utm_source` / тип реферера).
- **FR-024**: События PDP MUST содержать `sku` и `category_slug` товара.

### Functional Requirements — Атрибуция и UTM

- **FR-030**: Система MUST принимать и сохранять в cookie со сроком жизни 365 дней следующие метки из URL: `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `yclid`, `gclid`, `_openstat`, `from`. Все остальные параметры запроса игнорируются как метки атрибуции.
- **FR-031**: Корзина MUST хранить метки первого касания (first-touch) — устанавливаются при создании корзины и не перезаписываются.
- **FR-032**: При конверсии корзины в заказ метки атрибуции MUST копироваться в заказ (Order) без изменений.
- **FR-033**: При изменении статуса заказа на «оплачен» система MUST автоматически отправлять офлайн-конверсию в Яндекс.Метрику с привязкой к сохранённому `yclid` (если он есть) и сумме заказа.
- **FR-034**: При отсутствии `yclid` система MUST отправлять офлайн-конверсию с `client_id` Метрики (если он был сохранён в момент конверсии).
- **FR-035**: Cтраницы лендингов и продукта MUST корректно обрабатывать ссылки с параметрами атрибуции и не разрушать SEO-канонические URL (`?utm_*` исключены из канонической версии).

### Functional Requirements — Серверные события и устойчивость

- **FR-040**: Система MUST отправлять серверный хит `purchase` из бэкенда после подтверждённого webhook успешной оплаты — с тем же `transaction_id`, что используется в клиентском событии (равен номеру заказа), чтобы избежать дублирования.
- **FR-041**: Система MUST отправлять серверный хит `rfq_submit` из бэкенда при успешном приёме RFQ-запроса.
- **FR-042**: Серверные хиты MUST содержать `client_id` Метрики, если он был передан с клиента в момент конверсии; иначе использовать стабильный заместитель на базе сессии.
- **FR-043**: Серверные хиты MUST НЕ отправляться, если у пользователя нет согласия на аналитику-cookie на момент конверсии (если согласие было дано при checkout, оно считается достаточным для всей конверсии).
- **FR-044**: Сбой отправки серверного хита MUST НЕ приводить к сбою основной операции (оформление заказа/RFQ); ошибка только логируется.

### Functional Requirements — Цели Метрики и воронки

- **FR-050**: В Яндекс.Метрике MUST быть настроены цели на следующие события (через UI Метрики, ID хранятся в админ-настройках сайта): `rfq_submit`, `add_to_cart`, `begin_checkout`, `purchase`, `quick_order_submit`, `invoice_request_submit`, `document_download`, `phone_click`, `email_click`, `callback_request_submit`, `filter_apply`, `search`, `qualified_visit` (micro-goal, см. FR-210), `price_request_click` (см. FR-190).
- **FR-051**: В Метрике MUST быть настроены составные цели (воронки): **«Покупка детально»** (Главная/Лендинг → PDP → `add_to_cart` → `begin_checkout` → `checkout_step_contact` → `checkout_step_shipping` → `checkout_step_payment_method` → `checkout_step_review` → `checkout_cta_pay_clicked` → `payment_intent` → `purchase`); «RFQ» (PDP → `add_to_cart` → `rfq_open` → `rfq_submit`); «Быстрый заказ» (Каталог → `quick_order_submit`); «Документы» (PDP → `document_download`); «B2B запрос цены» (PDP → `price_request_click` → `rfq_submit` или `callback_request_submit`).
- **FR-052**: Главная цель «Покупка» MUST быть основной целью счётчика для Директа (используется при оптимизации ставок). Цель `qualified_visit` MUST быть прописана как micro-conversion для оптимизации Директа на холодных кампаниях, где конверсий в `purchase` ещё мало.

### Functional Requirements — Webvisor, тепловые карты, приватность

- **FR-060**: Поля с ПДн (email, телефон, ФИО, ИНН, текст комментария / описания / ТЗ) MUST быть помечены так, чтобы их содержимое не передавалось в Webvisor и не записывалось в его архив. Это касается всех форм сайта: RFQ, checkout (физ/юр), быстрый заказ, callback, регистрация, восстановление пароля.
- **FR-061**: Webvisor MUST оставаться активным для нечувствительных частей страниц (карточки, кнопки, навигация).
- **FR-062**: Параметры всех событий MUST НЕ содержать значений ПДн (email, телефон, ФИО, ИНН, текст комментария).
- **FR-063**: Тепловые карты и карты ссылок MUST быть включены.

### Functional Requirements — Web Vitals и качество страниц

- **FR-070**: Система MUST измерять и отправлять в Метрику показатели Web Vitals — LCP (Largest Contentful Paint), CLS (Cumulative Layout Shift), INP (Interaction to Next Paint) — как параметры визита или первого page-view.
- **FR-071**: Показатели Web Vitals MUST быть видны в Метрике с разбивкой по типу страницы (`page_type`), чтобы можно было определить, какие шаблоны страниц медленные.

### Functional Requirements — Боты и качество трафика

- **FR-080**: Каждое событие/визит MUST содержать параметр `visitor_type` со значением `human` или `bot`. Классификация выполняется по User-Agent и набору известных шаблонов AI-bot / поисковых ботов, конфигурируемому через настройки админ-панели.
- **FR-081**: В Метрике MUST быть сохранён сегмент «Исключить ботов» для использования во всех ключевых отчётах и воронках.

### Functional Requirements — Недельный отчёт

- **FR-090**: Система MUST предоставлять способ автоматически сформировать отчёт за выбранный недельный диапазон (понедельник—воскресенье).
- **FR-091**: Отчёт MUST включать секции:
  - **Воронка покупки детальная** (с шагами checkout + drop-off);
  - **Воронка RFQ**;
  - **Источники (общая)** — по `acquisition_channel` (FR-240); ROAS по рекламным кампаниям из FR-301;
  - **Организический канал — Я.Вебмастер** (FR-230): топ-30 запросов, brand vs non-brand доля, новые/потерянные запросы и landing, статус sitemap и индекса;
  - **Организический канал — GSC** (FR-231): аналогично для Google;
  - **AI-поисковики** (`organic_ai`, FR-240): отдельной строкой с визитами, конверсиями;
  - **Schema-org effectiveness** (FR-234): страницы с rich snippets / featured snippets, динамика;
  - **Топ-запросов с конверсиями** (FR-243): пересечение Webmaster post-click и Метрики;
  - **Кластерный анализ** (FR-260, FR-261): impressions/clicks/conversions по кластерам + risk-кластеры;
  - **Качество индекса** (FR-252): топ-10 URL с ростом 404, число Soft 404, длинные редирект-цепочки, high-severity список;
  - **Организические PDF-скачивания** (FR-262);
  - **Внутренний поиск**: топ-запросы (FR-130), топ-без-результата (FR-131);
  - **Электронная коммерция**: топ-5 товаров, средний чек, выручка по категориям и брендам (FR-110…FR-112);
  - **Total RFQ/Orders/Revenue**;
  - **Качество визита**: доля `qualified_visit` (FR-210);
  - **B2B-сигналы**: `price_request_click` (FR-190), `inn_validation_failed` (FR-192), `print_page`, `copy_text` (FR-018, FR-019);
  - **Когорты и retention**: D7/D14/D30/D60, медианное `time_to_purchase` (FR-180…FR-183);
  - **Consent rate**: accept/decline/no-action (FR-282);
  - **Качество данных**: доля ботов (FR-080), доля визитов с JS-ошибкой (FR-173), число серверных хитов в очереди/failed (FR-311);
  - **Аннотации недели** (FR-160…FR-162): деплои, кампании, инциденты на таймлайне;
  - **Динамика к предыдущей неделе** (% по ключевым показателям).
- **FR-092**: Отчёт MUST сохраняться как версионируемый текстовый артефакт (MD) в репозиторий по пути `06-reports/analytics/YYYY-WW.md` — это canonical источник истины с git-history.
- **FR-093**: При недоступности API Метрики команда формирования MUST возвращать понятную ошибку и НЕ создавать частичный файл отчёта.
- **FR-094**: Payload admin MUST содержать страницу `/admin/analytics-report` со следующей функциональностью: список всех доступных недельных отчётов (по убыванию даты), при открытии конкретной недели — HTML-рендеринг соответствующего MD-файла из `06-reports/analytics/` с дополнениями: графики динамики ключевых показателей (неделя-к-неделе), кликабельные ссылки на отчёты Метрики и Я.Вебмастера (с pre-filled диапазоном и сегментами), таймлайн аннотаций (FR-160…FR-162). Источник данных — тот же MD; страница НЕ хранит копию данных в БД (без дублирования источника истины).
- **FR-095**: Страница `/admin/analytics-report` MUST быть доступна только администраторам Payload (RBAC), как и весь admin-route.

### Functional Requirements — SEO weekly: интеграция Я.Вебмастера и Google Search Console

- **FR-230**: Через API Яндекс.Вебмастера система MUST импортировать в недельный отчёт: топ-30 поисковых запросов недели (запрос, показы, клики, CTR, средняя позиция), топ-30 landing-pages по органическим кликам, покрытие индекса (in_index / excluded / errors с разбивкой по причине), статус sitemap (дата последнего обращения, число принятых URL, число ошибок).
- **FR-231**: Через API Google Search Console система MUST импортировать аналогичный набор данных для Google.
- **FR-232**: Каждый запрос MUST классифицироваться как brand (содержит «soliton», «солитон» и распознаваемые транслитерации/опечатки) или non-brand; в отчёте видна доля brand-кликов от общего organic-объёма.
- **FR-233**: Запросы и landing-pages, попавшие в топ-100 впервые на этой неделе ИЛИ потерянные (были на прошлой, нет на этой), MUST выводиться в отдельных списках «новые запросы» / «потерянные запросы» / «новые landing» / «потерянные landing».
- **FR-234**: Через API Я.Вебмастера и GSC система MUST импортировать список страниц с активными rich-snippets / featured-snippets / быстрым ответом; в отчёте — секция «Schema-org effectiveness» с динамикой к прошлой неделе.
- **FR-235**: Подключение Webmaster/GSC требует подтверждённого владения доменом и валидных учётных данных (service account для GSC, OAuth-token для Я.Вебмастера); хранятся в конфигурации, как описано в FR-100.

### Functional Requirements — Классификация реферера и атрибуция организики

- **FR-240**: Каждый визит MUST получать параметр `acquisition_channel` из закрытого списка: `organic_yandex`, `organic_google`, `organic_images_yandex`, `organic_images_google`, `organic_maps_yandex`, `organic_maps_google`, `organic_marketplace_yandex_market`, `organic_ai` (Perplexity, ChatGPT, Claude, Алиса-нейро, GigaChat, You.com, Phind), `paid_yandex_direct` (визит с yclid), `paid_google_ads` (визит с gclid), `social` (vk.com, t.me, facebook.com и др.), `marketplace_outbound` (входящий с маркетплейса), `direct` (нет реферера), `referral` (всё остальное).
- **FR-241**: Списки host-паттернов для каждой категории MUST храниться как конфигурация в админ-настройках (а не зашиты в код), чтобы новый AI-поисковик / соц-сеть можно было добавить без релиза.
- **FR-242**: Для визитов из `organic_yandex` система MUST пытаться извлечь поисковый запрос из URL referer (параметр `text=`) и сохранять как `acquisition_query` в Cart и Order. Поисковая фраза в общем случае не считается ПДн по 152-ФЗ; но если в ней внезапно обнаружен email/телефон — фраза не сохраняется.
- **FR-243**: В weekly-отчёте MUST быть таблица «Топ-запросов с конверсиями» — на пересечении данных post-click report Я.Вебмастера и Метрики (Webmaster предоставляет связку «запрос → URL → клики», Метрика добавляет конверсии этих URL).

### Functional Requirements — Crawl errors, Soft 404 и индекс-санитар

- **FR-250**: Система MUST логировать каждый ответ сервера 404, 410, 5xx, а также длинные редирект-цепочки (>1 hop) для известных поисковых ботов (`YandexBot`, `Googlebot`, `Mail.ru`, `Bingbot`) с URL, статусом, user-agent, временем.
- **FR-251**: Система MUST детектировать Soft 404 — страницы, возвращающие 200, но содержащие маркеры «не найдено / нет в наличии / снят с производства / категория удалена»: таким страницам в payload `page_view` ставится `is_soft_404=true`.
- **FR-252**: В weekly-отчёте MUST быть секция «Качество индекса»: топ-10 URL с ростом 404 за неделю, число Soft 404 страниц, число длинных редирект-цепочек, статус sitemap из FR-230, число «исключённых» страниц в Webmaster/GSC с разбивкой по причине.
- **FR-253**: Появление 404 на индексной странице (есть в sitemap или в индексе Webmaster/GSC) MUST классифицироваться как high-severity и подсвечиваться в отчёте красным; такие URL включаются в список «исправить срочно».

### Functional Requirements — Кластер и landing-page анализ

- **FR-260**: Параметр визита `cluster` (FR-021) MUST использоваться для агрегации organic-производительности по SEO-кластерам: для каждого кластера в weekly-отчёте — organic-impressions (из Webmaster), clicks, conversions, conversion-rate.
- **FR-261**: Outlier-детекция: если кластер за неделю потерял ≥30% impressions ИЛИ ≥30% conversions относительно прошлой недели, в отчёте он подсвечивается как «risk-кластер» с рекомендацией проверить.
- **FR-262**: PDF-документы (документация, паспорта, сертификаты), которые индексируются поисковиками, MUST иметь регистрацию органического скачивания: либо через серверный хит при отдаче PDF с реферером поисковика, либо через промежуточный landing с JS-инициализацией перед скачиванием. В weekly-report — секция «Organic PDF downloads».

### Functional Requirements — Изоляция test/staging и production

- **FR-270**: Production-счётчик Я.Метрики и GA4 MUST использоваться только в production-окружении. В dev/staging инициализация Метрики использует отдельный test-счётчик ИЛИ полностью отключена через env-flag.
- **FR-271**: Каждое событие MUST содержать параметр `env` со значением из закрытого списка (`production`, `staging`, `development`) — даже когда test-счётчик отдельный, это страховка от случайной утечки.
- **FR-272**: Раз в сутки автоматическая проверка production-счётчика MUST фильтровать визиты с `env != production`; если такие есть, система алертит в admin (значит, что-то настроено неправильно), а в weekly-отчёте за этот период проставляется метка «возможно загрязнённые данные».

### Functional Requirements — Cookie-banner: мета-аналитика согласия

- **FR-280**: Система MUST отправлять событие `consent_banner_shown` при первом показе cookie-баннера в визите. Поскольку Метрика ещё не инициализирована до согласия, событие либо буферизуется в cookie и отправляется при ближайшей возможности (после accept), либо логируется серверно как факт «баннер показан N раз».
- **FR-281**: При выборе пользователем варианта баннера система MUST отправлять `consent_accepted` или `consent_declined`. Для declined визит не получает Метрика-хитов; факт отказа фиксируется только серверно. Если в будущем появится granular consent — параметр `consent_categories=[...]` (например, `analytics`, `marketing_retargeting`).
- **FR-282**: В weekly-отчёте MUST быть секция «Consent rate»: процент accept / decline / no-action; владелец видит, какая доля трафика «теневая» (без аналитики из-за отказа). При accept-rate < 50% — отдельный алерт «банер скорее всего проблемный».

### Functional Requirements — Pre-deploy smoke test и goal-mapping

- **FR-290**: Smoke-test событий MUST исполняться в двух слоях:
  - **Слой 1 — jsdom/vitest, на каждом PR** (быстро, секунды): прогоняет все event-helpers из `lib/analytics/events.ts`, проверяет структуру `dataLayer.push(...)` для каждого события (FR-001…FR-019, FR-110…FR-125, FR-280…FR-281, FR-320), валидирует обязательный набор параметров и отсутствие ПДн в payload (email/phone/ФИО/ИНН/комментарий). Реализуется как `pnpm test:analytics:unit`.
  - **Слой 2 — Playwright headless, перед production-деплоем**: реальный браузер прогоняет конверсионные пути (PDP → add_to_cart → checkout step-by-step → purchase ИЛИ RFQ-submit), плюс события, требующие реальных браузерных API (`scroll_depth_*` через Intersection Observer; `print_page` через `window.matchMedia('print')` / `beforeprint`; first-party cookies Метрики из FR-340). Реализуется как `pnpm test:analytics:e2e`.
- **FR-291**: Несоответствие любого из двух слоёв (отсутствует ожидаемое событие, неверный набор параметров, утечка ПДн, лишний/недостающий `transaction_id`) MUST блокировать production-деплой (CI fail). Локальные сборки запускают слой 1 по умолчанию; слой 2 — опционально через `pnpm test:analytics:e2e --headed`.
- **FR-292**: Список целей Метрики (event_name → metrika_goal_id → ga4_event_name → business_meaning → owner) MUST храниться как версионируемый артефакт `06-reports/analytics/goal-mapping.md`; обновляется синхронно с любым PR, который меняет события или цели.
- **FR-293**: Goal-mapping artifact MUST служить источником правды для smoke-теста: какие именно события smoke ожидает увидеть, берётся отсюда.

### Functional Requirements — Импорт стоимости Я.Директа и ROAS

- **FR-300**: Метрика-счётчик MUST быть привязан к аккаунту Я.Директа через стандартный UI Метрики, что включает автоимпорт стоимости рекламных кампаний (по yclid). Это даёт колонку «Расход» в отчёте «Источники → Метки → Кампания».
- **FR-301**: При наличии импорта в weekly-отчёте для каждой рекламной кампании виден ROAS = revenue / cost; кампании с ROAS<1 подсвечиваются.
- **FR-302**: При отсутствии импорта (счётчики не связаны) секция «Эффективность Директа» содержит явную пометку «связка Метрика↔Директ не настроена», а не тихо скрывается. Owner может настроить связку через UI Метрики и пометка пропадёт со следующей недели.

### Functional Requirements — Resilience серверных хитов: retry-очередь

- **FR-310**: Серверные хиты (FR-040…FR-044) MUST отправляться через очередь с retry: при сбое (network error, 5xx от Метрики, timeout) задача попадает в очередь `pendingAnalyticsHits` с экспоненциальным backoff (1 мин → 5 мин → 30 мин → 2 ч → 24 ч).
- **FR-311**: После 5 неудачных попыток задача помечается как `failed` и логируется в admin alerting; не теряется без следа и не блокирует основную операцию заказа/RFQ.
- **FR-312**: Очередь MUST быть идемпотентной: при retry проверяется актуальность задачи (заказ не отменён, статус не «refunded»); повторная отправка одного `transaction_id` не создаёт дубля в Метрике (это уже обеспечено FR-040 через `transaction_id`, но и очередь должна сама проверять).

### Functional Requirements — Базовое событие `page_view`

- **FR-320**: Каждый просмотр публичной страницы MUST отправлять событие `page_view` с параметрами `page_type`, `path`, `cluster?`, `is_soft_404?`, `acquisition_channel?` — это страховочное событие для всех страниц, которые не покрываются специализированными FR (главная при первом визите, knowledge-статьи, B2B-landing, info/*, /about, /contacts, ошибочные страницы). Совмещается с автоматическим page-view Метрики, но даёт явное событие в `dataLayer` для построения custom-funnel.

### Functional Requirements — Webhook на достижение целей

- **FR-330**: Я.Метрика MUST конфигурироваться так, чтобы при достижении ключевых целей (`purchase`, `rfq_submit`, `payment_failed` с reason ∈ {`payment_method_declined`, `webhook_timeout`}) отправлять webhook на внутренний endpoint сайта, который ретранслирует в admin-alerting (Telegram-канал / email-список).
- **FR-331**: Endpoint обработки Метрика-webhook MUST верифицировать подпись (или IP-allowlist Метрика-серверов), быть идемпотентным и не создавать спам при ретраях Метрики.

### Functional Requirements — Safari/ITP resilience: first-party cookies Метрики

- **FR-340**: Я.Метрика MUST инициализироваться с включённой опцией «первичные cookie» (настраивается в UI счётчика Метрики): cookies `_ym_*` ставятся на домене сайта (или его поддомене), а не на `mc.yandex.ru`, чтобы пережить Apple ITP и сохранить атрибуцию для Safari/iOS-посетителей.
- **FR-341**: Если сайт использует CDN/CNAME, в конфигурации DNS MUST быть прописана корректная связка для first-party cookies; администратор валидирует это перед запуском (одна из задач deploy-чек-листа).

### Functional Requirements — 152-ФЗ data subject access для аналитики

- **FR-350**: В составе деливерабла этой спеки MUST быть создан runbook `06-reports/analytics/dsar-runbook.md`, описывающий процедуру ответа на запрос пользователя «какие аналитические данные обо мне есть»: как достать `_ym_uid` пользователя, какие визиты и webvisor-записи с ним связаны, как сформировать ответ.
- **FR-351**: Runbook MUST описывать процедуру удаления аналитических данных пользователя: использование API Метрики для удаления визита, удаление конкретной webvisor-записи, удаление связанных событий из любых server-side аналитических очередей.
- **FR-352**: Все DSAR-запросы (access / delete) на аналитические данные MUST логироваться в admin audit log с инициатором, датой, типом запроса, сроком выполнения (по 152-ФЗ — 30 дней).

### Functional Requirements — Электронная коммерция (нативный формат Яндекс.Метрики)

- **FR-110**: Параллельно с event-разметкой (FR-001…FR-019) система MUST отправлять в `dataLayer` объект `ecommerce` в нативном формате Метрики, чтобы активировался встроенный отчёт «Электронная коммерция»: операции `detail` (просмотр товара), `add` (в корзину), `remove` (из корзины), `purchase` (оплата) с обязательными полями `id`, `name`, `category`, `brand`, `variant`, `price`, `quantity`, `currencyCode=RUB`.
- **FR-111**: Объект `ecommerce.purchase` MUST содержать `actionField.id`, равный номеру заказа (= `transaction_id`), а также `revenue` (товары без доставки), `shipping`, `tax` — отдельными полями.
- **FR-112**: Каждый товар в `ecommerce.products[]` MUST включать `category` и `brand`, чтобы отчёт «Электронная коммерция → Заказы → Категории/Бренды» агрегировался корректно.
- **FR-113**: При просмотре листинга (главная, каталог, категория, поиск) MUST отправляться `ecommerce.impressions` с массивом видимых позиций и их позицией в списке (`list`, `position`), чтобы был отчёт «Видимость товаров».
- **FR-114**: `transaction_id` в ecommerce-объекте и в обычном событии `purchase` MUST совпадать — это базовое условие, чтобы конверсия не считалась дважды.
- **FR-115**: Состав ecommerce-объекта MUST НЕ содержать ПДн ни в одном поле (`name` товара не идентифицирует покупателя; добавлять покупательские поля сюда запрещено).

### Functional Requirements — Шаги внутри checkout

- **FR-120**: Система MUST отправлять `checkout_step_contact` при первом фокусе/заполнении блока контактных данных в checkout.
- **FR-121**: Система MUST отправлять `checkout_step_shipping` при показе/первом взаимодействии с блоком выбора доставки.
- **FR-122**: Система MUST отправлять `checkout_step_payment_method` при показе блока выбора способа оплаты.
- **FR-123**: Система MUST отправлять `checkout_step_review` при показе сводки заказа перед нажатием «Оплатить».
- **FR-124**: Система MUST отправлять `checkout_cta_pay_clicked` при клике на финальную кнопку оплаты (до редиректа на платёжный шлюз).
- **FR-125**: Все checkout-step события MUST содержать параметры `step_index` (1..5) и `checkout_type` (`physical`, `legal`, `quote`) — для построения детализированной воронки и сегментации по типу оформления.

### Functional Requirements — Поиск и встроенный отчёт «Внутренний поиск»

- **FR-130**: При отправке события `search` (FR-004) система MUST дополнительно конфигурировать встроенный отчёт «Внутренний поиск» Метрики — передавать запрос через специальный параметр визита, чтобы агрегатор Метрики формировал отчёт «Поисковые запросы по сайту».
- **FR-131**: При нулевом результате поиска система MUST отправлять отдельное событие `search_no_results` с `search_term` — это сигнал для контент-стратегии (новые карточки/категории/landing).
- **FR-132**: Система MUST отправлять `search_refinement` при изменении запроса в течение одной поисковой сессии (без перезагрузки страницы) — для оценки качества первого результата.

### Functional Requirements — Call-tracking архитектурная готовность

- **FR-140**: Все телефонные номера на сайте (шапка, подвал, контакты, PDP, formы) MUST рендериться через единый компонент-обёртку, в которую позже можно подставить динамический номер от call-tracking-сервиса без изменения каждой страницы.
- **FR-141**: При показе телефона система MUST отправлять событие `phone_displayed` с параметрами `displayed_number` (показанный номер) и `acquisition_channel` (источник из метки атрибуции) — это закрывает gap «какой номер увидел пользователь по какой кампании».
- **FR-142**: Все DOM-узлы с телефонами MUST содержать стабильный data-атрибут идентификации слота (например `data-phone-slot="header"`), чтобы внешний call-tracking-сервис мог подменить номер без вмешательства в layout.

### Functional Requirements — Кросс-устройства (привязка customer_id)

- **FR-150**: Для авторизованных посетителей (магнит-логин по спеке 054) система MUST передавать в Метрику стабильный параметр пользователя `UserID` равный внутреннему `customer_id` (UUID или числовой ID Payload), чтобы Метрика связывала визиты одного человека с разных устройств в один профиль.
- **FR-151**: `UserID` MUST НЕ содержать ПДн (не email, не телефон, не ФИО). Используется только opaque-идентификатор.
- **FR-152**: При выходе из аккаунта система MUST очистить `UserID` в Метрика-сессии так, чтобы новые визиты этого браузера уже не привязывались к customer.

### Functional Requirements — Аннотации релизов и инцидентов

- **FR-160**: Каждый деплой в production MUST автоматически создавать запись аннотации с типом `deploy` (поля: дата/время, git-ref, краткое описание, ссылка на PR) — для последующего сопоставления с просадками/ростом метрик.
- **FR-161**: Значимые события (запуск кампании, инцидент, выпуск новой категории, ценовая акция) MUST добавляться вручную через админ-панель или CLI-команду в тот же реестр аннотаций.
- **FR-162**: Аннотации MUST отображаться в недельном отчёте на таймлайне рядом с графиками конверсий, чтобы owner мог визуально соотнести «вчера выкатили X → конверсия упала на Y%». Локальные/dev-деплои в этот реестр не попадают.

### Functional Requirements — Ошибки сайта и устойчивость

- **FR-170**: Глобальный обработчик JavaScript-ошибок (`window.onerror` + `unhandledrejection`) MUST отправлять событие `js_error` с параметрами `error_message`, `source_file`, `line_number`, `page_type`, `user_agent_class` (mobile/desktop/bot). ПДн в ошибках не передаются (если в `error_message` подмешано пользовательское значение — оно вырезается фильтром).
- **FR-171**: Страницы 404 MUST отправлять событие `page_404` с `requested_path` и `referrer`.
- **FR-172**: Страницы серверных ошибок (5xx) MUST отправлять событие `error_5xx` с `status_code` и `endpoint`.
- **FR-173**: В Метрике MUST быть настроен сегмент «Визиты с JS-ошибкой» — чтобы «сломанные» сессии отделять от воронки и не путать с осмысленным drop-off.

### Functional Requirements — Когорты, retention и time-to-purchase

- **FR-180**: Система MUST собирать сигналы для когортного анализа: `first_seen_at`, `visit_number`, флаг возвращающегося посетителя, флаг устройства (mobile/desktop/tablet). Источник `first_seen_at` — гибридный: для анонимных посетителей primary-источник — cookie `_solitomo_first_seen` (TTL 365 дней, не перезаписывается при последующих визитах). Для авторизованных Customer-ов (спека 054) система MUST хранить поле `customer.firstSeenAt` в Payload; при первом логине backend записывает `min(cookie._solitomo_first_seen, existing customer.firstSeenAt)`. При последующих визитах с тем же `customer_id` используется backend-value, что обеспечивает устойчивость к чистке cookie (типичный B2B-сценарий: первый визит → стёр cookie → залогинился через неделю → купил, когорта корректна).
- **FR-181**: В Метрике MUST быть настроен отчёт «Когортный анализ» по неделям с retention rate D7, D14, D30, D60.
- **FR-182**: При оплаченном заказе система MUST вычислять и сохранять в записи заказа: `time_to_purchase_days` (от `first_seen_at` до конверсии) и `visit_count_to_purchase`.
- **FR-183**: Эти показатели MUST включаться в недельный отчёт (см. обновлённый FR-091): среднее, медиана, разбивка по `user_type` (anonymous / customer / legal_entity).

### Functional Requirements — B2B-сигналы интереса

- **FR-190**: На странице товара система MUST отправлять `price_view` если цена показана публично, или `price_request_click` если пользователь нажал «Запросить цену» для товара без публичной цены. Параметры: `sku`, `category_slug`.
- **FR-191**: На странице товара система MUST отправлять `stock_status_view` с параметром `stock_status` из закрытого списка (`in_stock`, `on_order`, `out_of_stock`, `unknown`) — для последующего отчёта «конверсия по доступности».
- **FR-192**: При валидации поля ИНН в формах юрлица система MUST отправлять `inn_validation_success` или `inn_validation_failed` (с кодом ошибки, без значения ИНН) — это CRO-сигнал «много fail → нужно улучшить поле».
- **FR-193**: События `print_page` (FR-018) и `copy_text` (FR-019) MUST использоваться как B2B-сигналы интереса; в недельном отчёте они выводятся в секции «B2B-сигналы».

### Functional Requirements — Ретаргетинговые сегменты

- **FR-200**: В Метрике MUST быть созданы и сохранены следующие именованные сегменты для последующего использования как аудиторий Я.Аудиторий / Директа: «Добавил в корзину, не купил, ≥1 визит за 7 дней»; «Скачал документацию»; «Заполнил RFQ, не отправил»; «Купил товар (для cross-sell)»; «Юрлицо» (`user_type=legal_entity`); «Совершил ≥1 покупку за 90 дней» (для LTV-апселла); «Просмотрел ≥3 PDP за визит, не купил» (high-intent); «Нажал `price_request_click`, не отправил RFQ» (B2B-теплый лид).
- **FR-201**: Каждый сегмент MUST быть проверен: счётчик визитов в сегменте больше нуля после первой недели запуска (если ноль — разметка где-то не отработала, требуется отладка).
- **FR-202**: Сегменты MUST быть синхронизированы с аудиториями Я.Аудиторий / Директа (через стандартный UI Метрики), чтобы маркетолог мог запустить ретаргетинговую кампанию без переделки разметки.

### Functional Requirements — Качественный визит (micro-goal для рекламы)

- **FR-210**: В Метрике MUST быть настроена цель `qualified_visit` со стартовыми критериями: длительность визита ≥ 30 секунд, глубина просмотра ≥ 2 страниц, посетитель не классифицирован как бот, визит не отказной (bounce=false). Эту цель используют в Директе как micro-conversion для оптимизации ставок на «холодных» кампаниях, где конверсий в `purchase` ещё мало.
- **FR-211**: Параметры цели `qualified_visit` MUST храниться как конфигурация (не зашиты в код), чтобы при росте трафика их можно было ужесточить (например, ≥ 60 сек / ≥ 3 страниц).

### Functional Requirements — Operator manual (документация для маркетолога)

- **FR-220**: В составе деливерабла этой спеки MUST быть создан текстовый артефакт `06-reports/analytics/operator-guide.md` с: глоссарием всех событий (имя → бизнес-смысл → где смотреть), описанием каждой воронки и сегмента, инструкцией «как читать недельный отчёт за 30 минут», списком обязательных проверок при запуске новой рекламной кампании (UTM-чек-лист, минимальный набор сегментов, окно атрибуции).
- **FR-221**: При изменении состава событий, сегментов или целей operator-guide MUST обновляться синхронно с кодовыми изменениями (это часть definition-of-done для любого PR, меняющего аналитику).

### Functional Requirements — Конфигурация и эксплуатация

- **FR-100**: **Все runtime-секреты MUST храниться в env-переменных** (production env / `.env` для локальной разработки); никогда не коммитятся в git. Это включает: ID счётчика Я.Метрики и GA4 (`NEXT_PUBLIC_*` — публичные, но всё равно через env), token API Я.Метрики, OAuth-token Я.Вебмастера, service-account JSON для Google Search Console (хранится как base64-string или путь к файлу секрета на сервере), token Я.Директа (если потребуется явный), token Telegram-bot для admin-alerting, IP-allowlist для Метрика-webhook (если фиксированный). Ротация любого секрета требует redeploy (это сознательный trade-off в пользу простоты и устранения единого SPOF в БД).
- **FR-101**: Payload Globals → AnalyticsSettings содержат **только не-секретные конфигурации**, редактируемые админом без redeploy: список host-паттернов реферера (FR-241), список ботовых UA-шаблонов (FR-080), список Soft 404-маркеров (FR-251), список целей с их Metrika-Goal-ID (если синхронизируется руками с UI Метрики), флаги активации (Webvisor on/off, server-side hits on/off, qualified_visit пороги FR-211), brand-keyword список для FR-232.
- **FR-102**: В админ-панели MUST быть единая страница «Аналитика»: статус подключений (Метрика/GA4/Webmaster/GSC/Я.Директ — по наличию валидных env-переменных, БЕЗ показа значений), список настроенных целей, список ботовых шаблонов и host-паттернов реферера (редактируемые), ссылка на последний weekly-отчёт.
- **FR-103**: Изменение **не-секретных** настроек аналитики через Payload Globals (FR-101) MUST логироваться в audit log админки.
- **FR-104**: На странице «Аналитика» в админке MUST быть чек-лист «Готовность к production»: проверка наличия всех env-переменных, валидности OAuth-токена Webmaster (через тестовый API-вызов), доступности GSC, привязки счётчика к Я.Директу. Любое «красное» состояние подсвечивается, owner понимает, что ещё нужно настроить.

### Key Entities

- **AnalyticsEvent** — событие, отправляемое в Метрику и/или GA4. Атрибуты: имя события, параметры события (без ПДн), `transaction_id` для конверсионных событий, `page_type`, `user_type`, метка времени, идентификатор клиента Метрики, серверный/клиентский источник.
- **AttributionTouchpoint** — точка касания пользователя с рекламой/источником. Атрибуты: набор UTM-меток, `yclid`/`gclid`, реферер, время первого касания, признак first-touch/last-touch.
- **OfflineConversion** — событие конверсии, отправленное в Метрику с сервера после изменения статуса заказа. Атрибуты: тип конверсии (`purchase`), `transaction_id` (= номер заказа), сумма, валюта, `yclid`/`client_id`, признак, был ли продублирован клиент-side.
- **WeeklyReport** — артефакт отчёта за неделю. Атрибуты: период (week/year), секции (воронки, источники, ботометрика, динамика), путь сохранения, дата генерации.
- **AnalyticsSettings** — конфигурация системы. Атрибуты: идентификаторы счётчиков, список целей, ботовые шаблоны, признак активации серверных хитов, признак активации Webvisor, параметры `qualified_visit` (длительность/глубина), список обязательных ретаргетинговых сегментов.
- **EcommerceItem** — позиция в нативном ecommerce-объекте Метрики. Атрибуты: `id`, `name`, `category`, `brand`, `variant`, `price`, `quantity`, `position` (в списке), `currencyCode=RUB`.
- **CustomerLink** — связь между внутренним `customer_id` и визитами в Метрике через `UserID`. Атрибуты: `customer_id`, дата привязки, признак активности (logged-in / logged-out).
- **DeployAnnotation** — запись на таймлайне для соотнесения изменений сайта и динамики метрик. Атрибуты: тип (`deploy`, `campaign`, `incident`, `manual`), дата/время, git-ref (для deploy), краткое описание, ссылка на PR/тикет.
- **RetargetingSegment** — именованный сегмент аудитории в Метрике для последующего использования в Я.Аудиториях / Директе. Атрибуты: имя, правила сегментации, дата создания, признак синхронизации с Я.Аудиториями.
- **CohortRecord** — фиксированные на момент конверсии данные о цикле покупки. Атрибуты: `first_seen_at`, `visit_count_to_purchase`, `time_to_purchase_days`, `user_type`, `device_class`.
- **OperatorGuide** — артефакт документации `06-reports/analytics/operator-guide.md`. Содержит глоссарий событий, описание воронок/сегментов, чек-лист «как читать недельный отчёт», UTM-чек-лист для запуска кампании.
- **SearchConsoleQuery** — строка из API Я.Вебмастера / GSC. Атрибуты: `query_term`, `impressions`, `clicks`, `ctr`, `average_position`, `country`, `device`, источник (`yandex` / `google`), признак brand/non-brand, неделя.
- **IndexCoverageRecord** — состояние индексации страницы. Атрибуты: URL, статус (in_index / excluded / error), причина (если excluded/error), источник (Webmaster/GSC), дата последней проверки.
- **CrawlErrorRecord** — событие ошибочного ответа для поискового бота. Атрибуты: URL, status_code (404/410/5xx), bot_user_agent, время, признак high-severity (URL в sitemap/индексе).
- **ReferrerClassification** — правило классификации реферера. Атрибуты: host-паттерн, канал (`organic_yandex`, `organic_ai`, `social`, …), флаг brand-query (для search-источников), приоритет (когда несколько правил совпадают).
- **AcquisitionQueryRecord** — извлечённый поисковый запрос для визита (если referer поддерживает). Атрибуты: `query_term`, источник, время, привязка к корзине/заказу.
- **AnalyticsHitQueueItem** — запись в очереди retry для серверного хита. Атрибуты: payload, `transaction_id`, `attempts`, `next_retry_at`, `status` (`pending`/`failed`/`sent`), error_log.
- **GoalMappingEntry** — строка из `goal-mapping.md`. Атрибуты: event_name, metrika_goal_id, ga4_event_name, business_meaning, owner, дата последнего изменения.
- **MetrikaCounterEnvironment** — связка «окружение → counter_id». Атрибуты: env (`production`/`staging`/`development`), counter_id, enabled, последняя проверка корректности.
- **ConsentBannerInteraction** — событие/факт взаимодействия с cookie-баннером. Атрибуты: тип (`shown`/`accepted`/`declined`/`no_action`), категории (для granular consent), время.
- **DSARRequest** — запрос на доступ к или удаление аналитических данных. Атрибуты: инициатор (customer_id или `_ym_uid`), тип (`access`/`delete`), дата запроса, дата выполнения, статус, кто исполнил.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На основной user journey (Главная → PDP → Добавление в корзину → Checkout → Успешная оплата) в Яндекс.Метрике в течение 30 минут после действия видна полная воронка с количеством на каждом шаге; drop-off rate можно вычислить.
- **SC-002**: Все события из FR-001…FR-017 видны в режиме отладки Метрики на тестовой сессии «happy path»; ни одно ключевое событие не пропущено.
- **SC-003**: Владелец может за 30 минут получить готовый недельный отчёт (запуск инструмента + просмотр отчётов Метрики) и принять минимум одно решение «что чинить на сайте» по конкретным данным.
- **SC-004**: При покупке через ссылку с `?yclid=...` в записи заказа сохранены метки, а при переходе заказа в статус «оплачен» в Яндекс.Метрике в отчёте «Директ» в течение 24 часов появляется офлайн-конверсия с этим `yclid`.
- **SC-005**: Пользователь с активным adblock, прошедший оплату, виден в Метрике благодаря серверному хиту; повторный визит без adblock не создаёт дубль конверсии (дедупликация по `transaction_id` работает).
- **SC-006**: В выборочной проверке 10 случайных Webvisor-записей и payload-ов 20 случайных событий не найдено ни одного случая утечки email, телефона, ФИО, ИНН или текста комментария.
- **SC-007**: Показатели Web Vitals (LCP, CLS, INP) видны в Метрике в отчёте «Производительность» с разбивкой по типу страницы; известны 3 шаблона страниц с худшими значениями.
- **SC-008**: За первые две полные недели после запуска рекламы Метрика показывает не менее одного источника с измеримой конверсией (RFQ или заказ), а владелец может сравнить ROI разных кампаний.
- **SC-009**: При фильтре «не-боты» количество визитов уменьшается; владелец может видеть «чистую» воронку без AI-bot шума.
- **SC-010**: Историческая папка `06-reports/analytics/` после 4 недель работы содержит 4 файла, по одному на каждую полную неделю; динамика «неделя к неделе» рассчитывается автоматически.
- **SC-011**: В Метрике через 24 часа после первой покупки в production открывается отчёт «Электронная коммерция → Заказы» и показывает выручку, средний чек и хотя бы один товар в топе.
- **SC-012**: Воронка checkout с пятью шагами (`contact → shipping → payment_method → review → cta_pay_clicked`) видна в Метрике после первой полной недели, drop-off вычисляется на каждом шаге; владелец может назвать самый «узкий» шаг.
- **SC-013**: После 4 полных недель работы недельный отчёт показывает retention rate D7 и D30 и медианное `time_to_purchase_days`; этот показатель появляется и в Order.
- **SC-014**: Один и тот же авторизованный пользователь, открывший сайт с двух устройств подряд, отображается как один профиль в отчёте Метрики «Посетители» (благодаря привязке `UserID`).
- **SC-015**: Все обязательные ретаргетинговые сегменты (≥7 из FR-200) имеют ненулевой счётчик визитов в Метрике после двух недель работы.
- **SC-016**: При следующем production-релизе в недельный отчёт автоматически добавляется аннотация (тип `deploy`) с датой/git-ref и описанием — владелец видит её на таймлайне рядом с графиком конверсий.
- **SC-017**: Operator-guide (`06-reports/analytics/operator-guide.md`) прочитан маркетологом и принят как достаточный — маркетолог по чек-листу подтверждает, что понимает значение каждого события из FR-001…FR-019 и FR-110…FR-194.
- **SC-018**: В Метрике в отчёте «Поисковые запросы по сайту» виден список запросов; отдельно в недельном отчёте есть секция «топ-10 запросов без результатов» с не нулевым числом строк через две недели после запуска.
- **SC-019**: Цель `qualified_visit` срабатывает не реже чем для 10% обычных визитов (если меньше — порог слишком жёсткий и его нужно ослабить).
- **SC-020**: В weekly-report присутствуют секции «Организический канал — Я.Вебмастер» и «Организический канал — GSC» с не-нулевыми данными после первой полной недели запуска (при условии подтверждённого владения доменом).
- **SC-021**: В weekly-report отдельной строкой виден канал `organic_ai` с визитами от AI-поисковиков; список AI-источников можно дополнить через админ-настройки без релиза.
- **SC-022**: Brand vs non-brand split рассчитывается; доля brand-кликов представлена в отчёте; через 4 недели работы owner видит тренд («brand растёт» / «non-brand растёт» / «доля стабильна»).
- **SC-023**: В weekly-report виден consent-rate; accept-rate лежит в диапазоне 50…95% (если ниже — система алертит «банер скорее всего проблемный»).
- **SC-024**: Pre-deploy smoke-test покрывает не менее 80% обязательных событий из FR-001…FR-019 + FR-110…FR-125 + FR-280…FR-281 + FR-320; PR с регрессией (отсутствует ожидаемое событие) автоматически блокируется CI.
- **SC-025**: После привязки счётчика к Я.Директу в weekly-report появляется колонка «Стоимость» и ROAS для каждой активной рекламной кампании в течение 24-48 часов; кампании с ROAS<1 подсвечены.
- **SC-026**: При имитации временной недоступности `mc.yandex.ru` серверные хиты не теряются: попадают в `pendingAnalyticsHits`, после восстановления связи доходят до Метрики; в admin-alerting видны только реально провалившиеся (после 5 retry) задачи.
- **SC-027**: На Safari/iOS визиты атрибутируются корректно (first-party cookies Метрики работают): `_ym_uid` сохраняется ≥30 дней; доля «новых посетителей» в Safari в weekly-отчёте сопоставима с долей в Chrome (расхождение <20%).
- **SC-028**: Artifact `06-reports/analytics/goal-mapping.md` существует, версионируется, содержит маппинг для всех целей из FR-050; обновляется в том же PR, что меняет события или цели.
- **SC-029**: За 7 дней работы dev-сборок production-счётчик НЕ получает визитов с параметром `env != production`; суточная проверка зелёная.
- **SC-030**: На тестовый запрос «удалите мои аналитические данные» админ выполняет шаги runbook `dsar-runbook.md` менее чем за 30 минут; DSAR-запрос логируется в audit log.

## Assumptions

- **Согласие пользователя обязательно для аналитики.** Cookie-консент уже реализован в спеке 057; и клиентские, и серверные события отправляются только при наличии согласия (исключение — серверная страховка для уже paid-заказа, где согласие было дано в checkout).
- **Метрика — основной инструмент, GA4 — вторичный.** Серверные хиты, кастомные параметры, цели, воронки и отчёты делаются для Метрики. Тот же набор событий по возможности уходит и в GA4 (через тот же `dataLayer`), но без серверной части и без оптимизации под GA4.
- **Окно атрибуции — стандартное для Метрики (90 дней).** Любые конверсии вне этого окна теряют связку с кликом — это особенность платформы.
- **Атрибуция в Order — first-touch, в Метрике — last non-direct click.** Это сознательное расхождение: бизнесу важно знать «откуда пришёл пользователь изначально» (Order), а Метрика по умолчанию работает в last-touch модели.
- **AI-bot policy (отдельная спека 038) откладывается.** Эта спека лишь использует базовую детекцию ботов по User-Agent и параметр `visitor_type`; полная политика индексации и логирование AI-bot останутся в 038.
- **Twenty CRM пока выключен (спека 048).** Офлайн-конверсии из CRM («менеджер закрыл сделку») в v1 не реализуются; реализуется только офлайн-конверсия из изменения статуса заказа на «оплачен».
- **A/B-тестирование не входит в v1.** Это отдельная инициатива.
- **Метрика «Электронная коммерция» — теперь в scope (v2 ревью).** Параллельно с обычной event-разметкой система отправляет нативный объект `ecommerce` (см. FR-110…FR-115), чтобы был встроенный отчёт «Электронная коммерция» Метрики — без него нельзя получить выручку, средний чек, топ-товары и сегмент «купившие товар X».
- **Call-tracking сервис (Callibri / CallTouch / Comagic) — отдельная коммерческая интеграция.** Эта спека готовит архитектуру (FR-140…FR-142): обёртка-компонент для телефонов, data-атрибуты слотов, событие `phone_displayed`. Сам сервис подключается позже; благодаря готовности это не потребует переделки страниц.
- **Кросс-устройственная привязка — только для авторизованных.** Анонимные посетители остаются «по cookie/устройству». Это сознательное ограничение приватности: без логина нет надёжного способа объединить устройства без fingerprinting.
- **Когортный отчёт появляется не сразу.** Для retention D30 нужны 30 дней накопленных данных. В первый отчёт когорты могут быть пустыми — это нормально; разметка фиксирует данные с момента запуска.
- **Tag Manager (GTM Server-Side или Я.Tag Manager) — отдельная инициатива при ≥3 пикселях.** В v1 события отправляются прямой разметкой. Если в будущем добавится VK Ads / MyTarget / Telegram-пиксели — стоит вынести разметку в TM, чтобы не плодить дубли в коде.
- **Roistat / сквозная аналитика с CRM — после активации Twenty CRM (спека 048).** Связка Метрика + Директ + CRM = ROMI per source — отдельная спека.
- **Anomaly detection и алертинг — отдельная задача.** В v1 ограничиваемся weekly-отчётом и стандартными уведомлениями Метрики о целях.
- **Logs API Метрики → собственное хранилище — не в v1.** Метрика хранит raw-данные ~25 месяцев; долгосрочное хранение для исторического анализа — отдельная инфраструктура.
- **Конфигурация рекламы и создание кампаний не входит в скоуп.** Эта спека готовит инфраструктуру измерения; запуск рекламы — самостоятельный процесс на стороне маркетинга.
- **Подтверждение прав на домен в Я.Вебмастере и GSC — предусловие интеграции.** Выполняется владельцем отдельно через UI; без подтверждения соответствующие секции отчёта пустые с понятной пометкой.
- **API Я.Вебмастера имеет дневные лимиты запросов (~100/день).** Weekly-отчёт работает в пределах лимита за счёт кеша и группировки запросов; при превышении используется кеш предыдущей выгрузки с явной пометкой даты.
- **AI-поисковики могут не передавать корректный реферер.** Классификация работает best-effort: попадание в `organic_ai` — лишь когда узнаваемый host есть в списке. Новые AI-сервисы появляются часто, поэтому список конфигурируется (FR-241).
- **Я.Директ↔Метрика-связка — ручная настройка в UI.** Токен не нужен, но привязку делает владелец Метрика-счётчика через UI; без неё ROAS-секция явно пустая.
- **First-party cookies Метрики работают только если домен счётчика = домен сайта (или поддомен/CNAME).** Иначе ITP/Safari всё равно режет атрибуцию; требуется корректная DNS-настройка.
- **Поисковый запрос пользователя сам по себе не считается ПДн** по 152-ФЗ (если не содержит явных идентификаторов). Тем не менее перед сохранением `acquisition_query` система проверяет, нет ли в нём email/телефонной маски — если есть, не сохраняется.
- **Smoke-test событий не гарантирует корректность бизнес-логики.** Он проверяет факт push'а и набор параметров, но не их семантику; ручное тестирование сохраняется как back-stop.
- **Retry-очередь требует фоновой обработки.** Это означает необходимость cron-эндпоинта (по образцу существующих в проекте `/api/cron/*`).
- **Стандарт безопасности.** Токены API Метрики и идентификаторы счётчиков хранятся в env / зашифрованных полях; не коммитятся.

## Dependencies

- Спека 057 (`yookassa-buyer-info-compliance`) — opt-in cookie-консент и текущий загрузчик аналитики. Эта спека расширяет ту инфраструктуру.
- Спека 055/056 (`yookassa-payments-integration` + frontend) — события `purchase`, `payment_intent`, webhook-после-оплаты, `transaction_id`. Эта спека добавляет серверные дубликаты и расширенные `payment_failed`/`payment_retry`.
- Спека 054 (`customer-account`) — `customer_id` авторизованного посетителя для FR-150…FR-152 (кросс-устройства через Метрика-`UserID`). Без 054 эта часть не работает (graceful fallback на per-cookie).
- Спека 052 (`cart-as-entity`) — поле атрибуции на корзине (first-touch UTM) и перенос в Order при конверсии. Также хранит `first_seen_at` для FR-180.
- Спека 047 (`delivery-checkout-apiship`) — события доставки (FR-017) и блок выбора способа доставки (FR-121).
- Спека 048 (`twenty-crm-sync`) — пока выключена; при активации станет источником офлайн-конверсий (менеджер закрыл сделку). Не блокирует эту спеку.
- Спека 028 (`seo-canonical-check`) — критерии canonical-нарушений, потребляются FR-250 как часть «качества индекса».
- Спека 030 (`robots-refinement`) — robots.txt должен корректно разрешать YandexBot/Googlebot; иначе FR-230/231 не получит данных в Webmaster/GSC.
- Спека 040 (`machine-readable-product-feeds`) и 045 (`public-catalog-from-payload`) — sitemap-генерация для FR-230 (sitemap status).
- Спека 041 (`yandex-business-and-brand-presence`) — если Я.Бизнес-профиль активен, его трафик классифицируется отдельным каналом (`organic_maps_yandex`).

- Спека 044 (`mcp-server-soliton`) — при работе с AI-агентами полезно различать визиты от MCP-клиента от обычных AI-search визитов (раскладывать по `acquisition_channel`).

- Канонический документ `07-build-specifications/analytics-measurement-spec.md` — справочник, обновляется по итогам этой спеки.
