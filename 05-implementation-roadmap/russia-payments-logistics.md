# Оплата И Логистика В России Для Интернет-Магазина Soliton

Дата: 2026-05-12.

## Короткое Решение

Для Soliton нужно закладывать не один стандартный checkout, а гибридную модель:

1. **B2B-заявка / запрос КП** - основной сценарий для корпоративных клиентов.
2. **Оплата по счету для юрлиц** - счет, реквизиты, НДС, договор, закрывающие документы.
3. **Онлайн-оплата для частных покупателей** - карты Мир, СБП, платежная форма, фискализация по 54-ФЗ.
4. **Доставка через несколько служб** - СДЭК для ПВЗ/курьера, Деловые Линии для более тяжелых/корпоративных отправок, Boxberry/Почта России как дополнительные B2C-каналы.

Рекомендуемая стартовая связка:

- **ЮKassa** как основной платежный провайдер.
- **Т-Банк Эквайринг** или **CloudPayments** как альтернативный/резервный платежный провайдер.
- **СДЭК** как основной перевозчик для малых и средних отправлений.
- **Деловые Линии** для B2B-грузов и поставок в регионы.
- **Boxberry / Почта России** как дополнительные варианты для частных заказов, если появится такой спрос.

## Почему Нужна Гибридная Модель

Ассортимент Soliton - это технические товары: PDU, блоки розеток, устройства питания, аксессуары для стоек и серверных. Покупатель часто не просто кладет товар в корзину, а:

- уточняет совместимость;
- закупает несколько позиций;
- просит КП;
- работает от юрлица;
- хочет счет;
- просит доставку до объекта, склада, офиса или ЦОД;
- прикладывает ТЗ;
- согласует замену модели или комплектацию.

Поэтому обычная схема "товар - корзина - карта - доставка" должна быть, но она не должна быть единственным сценарием.

## 2. Абстрактный Слой Интеграций

В коде не нужно жестко привязывать checkout к одному провайдеру. Нужно сделать интерфейсы:

```ts
interface PaymentProvider {
  createPayment(order: Order): Promise<PaymentInitResult>
  handleWebhook(payload: unknown): Promise<PaymentWebhookResult>
  refund?(transactionId: string, amount: number): Promise<void>
}

interface ShippingProvider {
  calculate(input: ShippingCalculationInput): Promise<ShippingRate[]>
  createShipment(order: Order): Promise<ShipmentResult>
  getStatus(trackingNumber: string): Promise<ShipmentStatus>
  getPickupPoints?(city: string): Promise<PickupPoint[]>
}
```

Это позволит Codex добавлять и менять провайдеров без переписывания всего магазина.

## Оплата

## Рекомендуемый MVP

### 1. Оплата По Счету Для Юрлиц

Это первый обязательный сценарий.

На checkout нужно добавить:

- тип покупателя: физлицо / юрлицо;
- ИНН;
- КПП;
- название организации;
- юридический адрес;
- контактное лицо;
- email для счета;
- комментарий;
- кнопка "Получить счет" или "Запросить КП".

На первом этапе счет может формироваться менеджером вручную из заявки. На втором этапе можно генерировать PDF-счет автоматически.

### 2. Онлайн-Оплата Через ЮKassa

ЮKassa подходит как основной платежный провайдер, потому что:

- работает с российскими способами оплаты;
- поддерживает интернет-эквайринг;
- имеет API;
- поддерживает сценарии с 54-ФЗ и онлайн-кассой;
- понятна для российского бизнеса.

На сайте нужно реализовать:

- создание платежа через API;
- редирект клиента на платежную форму;
- webhook подтверждения оплаты;
- смену статуса заказа;
- возврат на страницу успешной оплаты;
- передачу данных для чека.

### 3. Резервный Провайдер

Стоит сразу спроектировать возможность второго провайдера:

- **Т-Банк Эквайринг** - сильный вариант, если расчетный счет и обслуживание будут в Т-Банке.
- **CloudPayments** - удобен для интернет-эквайринга и облачной фискализации.
- **Robokassa** - может быть резервным агрегатором, особенно если нужны разные способы оплаты.

Выбор второго провайдера лучше делать после понимания банка, расчетного счета, ставок и договора.

## 54-ФЗ И Фискализация

Для онлайн-оплаты физлицами нужно заранее учесть:

- онлайн-кассу;
- ОФД;
- формат фискальных данных;
- передачу номенклатуры;
- НДС;
- email/телефон покупателя для чека;
- чеки прихода и возврата;
- способ расчета и предмет расчета.

В карточках товаров и заказе нужно хранить данные, которые попадут в чек:

- название позиции;
- цена;
- количество;
- ставка НДС;
- признак предмета расчета;
- признак способа расчета.

Важно: финальную налоговую схему должен подтвердить бухгалтер или специалист по онлайн-кассам. В коде нужно заложить поля и события так, чтобы фискализация не была прикручена поверх заказа вручную.

## Логистика

## Рекомендуемый MVP

### 1. Доставка По Согласованию

Это обязательный вариант для B2B.

Показывать в checkout:

- "Доставка рассчитывается менеджером";
- "Самовывоз";
- "Доставка до объекта / склада";
- "Транспортная компания по согласованию".

Для многих корпоративных заказов этого достаточно на старте.

### 2. СДЭК

СДЭК стоит подключить первым как автоматизированную доставку:

- расчет стоимости;
- выбор ПВЗ;
- курьерская доставка;
- создание отправления;
- трек-номер;
- статусы.

На сайте:

- город доставки;
- карта/список ПВЗ;
- расчет срока и стоимости;
- сохранение выбранного ПВЗ в заказе.

### 3. Деловые Линии

Нужны для B2B и тяжелых/крупных поставок:

- расчет стоимости и сроков перевозки;
- терминалы;
- доставка до адреса;
- оформление заявки;
- получение статусов.

Для PDU и блоков розеток это может быть не первым сценарием, но для корпоративных поставок и региональных заказов его стоит заложить.

### 4. Boxberry / Почта России

Подключать после СДЭК, если будет заметный B2C-спрос:

- Boxberry - удобен для ПВЗ и интернет-магазинов.
- Почта России - шире покрытие, полезна для отдаленных регионов.

## Checkout-Сценарии

## Физлицо

1. Клиент выбирает товар.
2. Добавляет в корзину.
3. Выбирает город.
4. Выбирает доставку: СДЭК ПВЗ / СДЭК курьер / другая служба.
5. Видит итоговую цену.
6. Оплачивает онлайн.
7. Получает чек.
8. Получает трек-номер.

## Юрлицо

1. Клиент выбирает товары.
2. Добавляет в корзину или отправляет запрос КП.
3. Заполняет реквизиты.
4. Прикладывает ТЗ, если нужно.
5. Выбирает доставку: по согласованию / СДЭК / Деловые Линии.
6. Отправляет заявку.
7. Менеджер подтверждает наличие, цену, сроки.
8. Клиент получает счет / КП.
9. После оплаты заказ переводится в сборку и отгрузку.

## Что Нужно Учесть В SEO И UX

Оплата и доставка должны быть не только в checkout, но и на SEO-страницах:

- отдельная страница `/payment/`;
- отдельная страница `/delivery/`;
- блок "Оплата и доставка" на карточке товара;
- блок для юрлиц на категориях;
- FAQ про НДС, счет, КП, доставку до ЦОД, доставку транспортными компаниями;
- микроразметка `OfferShippingDetails` и `MerchantReturnPolicy`, если данные можно корректно поддерживать.

Для органического трафика это важно: покупатель технического товара часто ищет не только модель, но и условия поставки, оплату по счету, наличие, доставку в регион.

## Риски

- Нельзя запускать онлайн-оплату без корректной фискализации.
- Нельзя обещать точную стоимость доставки для B2B-грузов, если вес/габариты/упаковка не нормализованы.
- Нужно хранить вес и габариты товара, иначе расчет доставки будет неточным.
- Для юрлиц цена на сайте может отличаться от финального КП, поэтому нужно явно писать "цена от" или "уточняйте наличие и цену", если нет актуальных остатков.
- Webhook-и оплаты и логистики должны быть идемпотентными: повторное уведомление не должно ломать статус заказа.

Для оплаты и документов:
