# inSales И Работа Через Codex

Дата: 2026-05-13.

## Короткий Ответ

Да, Codex сможет помогать с inSales:

- готовить структуру сайта;
- писать тексты и SEO-метаданные;
- проектировать категории и посадочные;
- редактировать Liquid-шаблоны темы;
- писать HTML/CSS/JS для блоков;
- готовить инструкции для настройки админки;
- работать с API inSales;
- готовить массовый импорт товаров и статей;
- делать ТЗ для интеграций с МойСклад, оплатой и доставкой.

Но Codex не сможет управлять inSales так же полно, как собственным Next.js/Payload-проектом, потому что значительная часть inSales живет внутри SaaS-админки, настроек платформы и ограничений темы.

## Что Codex Сможет Делать Хорошо

## 1. Темы И Шаблоны

inSales использует Liquid-шаблоны. Если выгрузить тему в ZIP или дать доступ к файлам темы, Codex сможет:

- править `layout`;
- править шаблоны товара;
- править шаблоны коллекций/категорий;
- добавлять блоки на карточки;
- делать SEO-блоки;
- добавлять FAQ;
- добавлять микроразметку;
- править CSS и JavaScript;
- готовить новые сниппеты.

Это похоже на работу с Shopify Liquid: можно многое менять во внешнем виде и логике отображения, но нельзя полностью контролировать внутреннюю платформу.

## 2. Дополнительные Страницы

Codex сможет готовить:

- обычные текстовые страницы;
- статьи блога;
- SEO-лендинги на базе статей/страниц;
- категории с SEO-описаниями;
- страницы "Оплата", "Доставка", "Для юрлиц", "Запрос КП";
- контент для посадочных под PDU, блоки розеток, 19-дюймовые стойки, ЦОД, серверные шкафы.

Через API inSales доступны сущности вроде статей, блогов и коллекций, у которых есть SEO-поля: `html_title`, `meta_description`, `meta_keywords`, `permalink`, описание и контент.

## 3. Интеграции И Автоматизация

Codex сможет писать внешний интеграционный код:

- синхронизация с МойСклад;
- массовое обновление SEO-полей;
- генерация статей/посадочных;
- выгрузка/обработка заказов;
- обмен с CRM;
- отчеты по товарам и категориям.

Но такой код будет работать не внутри inSales, а на внешнем сервере или локально через API.

## Что Будет Сложнее

## 1. Настройки Админки

Codex может подготовить пошаговую инструкцию, но многие действия придется делать руками в админке:

- подключение платежей;
- настройка доставки;
- настройка приложений;
- настройки checkout;
- права доступа;
- некоторые параметры SEO;
- установка приложений.

Если дать браузерный доступ, Codex теоретически может помогать проходить по интерфейсу, но это менее надежно, чем работа с кодовым репозиторием.

## 2. Глубокая SEO-Архитектура

inSales позволит делать SEO-страницы, но с ограничениями:

- URL-структура задается платформой;
- индексируемые фильтры и сложные посадочные зависят от возможностей темы, приложений и платформы;
- сложнее сделать полностью собственную генерацию страниц;
- сложнее держать сайт как единый репозиторий;
- часть настроек будет разнесена между кодом темы, админкой и приложениями.

Для обычного магазина это нормально. Для максимального SEO под длинное семантическое ядро - хуже, чем Next.js.

## 3. B2B/RFQ-Логика

Можно сделать формы и страницы под юрлиц, но кастомная логика будет ограничена:

- запрос КП;
- сложные B2B-цены;
- договорные условия;
- прикрепление ТЗ;
- нестандартные статусы;
- кастомный checkout;
- сложные правила доставки и оплаты.

Часть можно решить приложениями и внешним API, но это уже гибридная схема.

## Практический Формат Работы С Codex На inSales

Чтобы Codex реально помогал, нужно организовать процесс так:

1. Выгружать тему inSales в ZIP.
2. Хранить тему в Git-папке проекта.
3. Давать Codex менять Liquid/CSS/JS локально.
4. Загружать обновленную тему обратно в inSales.
5. Для массовых операций использовать API-скрипты.
6. Вести отдельные таблицы/markdown-файлы с SEO-структурой, посадочными и текстами.

Такой процесс рабочий, но менее удобный, чем native code-first проект.

## Сравнение С Next.js/Payload

| Задача | inSales + Codex | Next.js/Payload + Codex |
|---|---:|---:|
| Быстро запустить магазин | 9/10 | 6/10 |
| Готовая интеграция с МойСклад | 9/10 | 6/10 |
| Править дизайн через код | 7/10 | 10/10 |
| Создавать SEO-посадочные | 6/10 | 10/10 |
| Управлять URL-структурой | 5/10 | 10/10 |
| Индексируемые фильтры | 5/10 | 10/10 |
| B2B/RFQ-логика | 5/10 | 10/10 |
| Все держать в Git | 5/10 | 10/10 |
| Работа Codex без ручной админки | 5/10 | 10/10 |

## Рекомендация

Если выбрать inSales, Codex сможет быть полезен, но больше как:

- SEO-архитектор;
- копирайтер и редактор карточек;
- разработчик темы;
- автор скриптов для API;
- помощник по настройке;
- проектировщик посадочных.

Codex не будет полноценным "разработчиком всего магазина", потому что ядро inSales закрыто и управляется через SaaS.

Для Soliton это означает:

- **inSales подходит**, если важны быстрый запуск, МойСклад, готовые оплаты/доставки и меньше разработки.
- **Next.js/Payload лучше**, если главный приоритет - максимальная SEO-архитектура, кастомный B2B-процесс и полная работа через Codex.

## Итоговое Решение

Выбирать inSales можно, если принять компромисс:

**быстрее запуск и проще интеграции, но меньше контроля для Codex и SEO.**

Если задача - построить максимально сильный органический сайт, где Codex сможет системно развивать структуру, страницы, контент, фильтры и B2B-логику, лучше остаться на Next.js/Payload.
