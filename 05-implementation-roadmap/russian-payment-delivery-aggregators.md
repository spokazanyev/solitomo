# Российские Агрегаторы Оплаты И Доставки Для Собственного Сайта Soliton

Дата: 2026-05-13.

## Короткий Ответ

Да, можно делать сайт на собственной технологии **Next.js + Payload + PostgreSQL** без inSales и подключить российские сервисы напрямую.

Но важно разделить:

- **модули inSales** нельзя нормально использовать отдельно от inSales, потому что это приложения внутри платформы inSales;
- **платежные агрегаторы** можно подключить к нашему сайту напрямую через API;
- **агрегаторы доставки** можно подключить к нашему сайту напрямую через API;
- **МойСклад** можно подключить напрямую через JSON API.

То есть правильная архитектура для собственного сайта:

```text
Next.js storefront
  -> Payload CMS
  -> PostgreSQL
  -> МойСклад API
  -> Payment Provider API
  -> Delivery Aggregator API
```

## Платежные Агрегаторы И Эквайринг

## 1. ЮKassa

Рекомендуемый основной вариант для Soliton.

Подходит для:

- оплаты картами;
- СБП;
- платежной формы;
- API-интеграции;
- счетов/ссылок на оплату;
- чеков и фискализации по 54-ФЗ;
- возвратов.

Плюсы:

- сильный российский платежный провайдер;
- понятная документация;
- готовые сценарии API;
- можно сделать кастомный checkout на собственном сайте;
- есть блок по чекам для налоговой.

Минусы:

- нужна аккуратная настройка 54-ФЗ;
- для B2B-счетов все равно нужен отдельный процесс по юрлицам.

## 2. Robokassa

Хороший вариант как агрегатор платежей и резервный провайдер.

Подходит для:

- карт;
- СБП;
- платежной формы;
- API;
- платежных ссылок;
- тестового режима;
- фискализации по 54-ФЗ.

Плюсы:

- прямо поддерживает самописные сайты через API;
- удобный быстрый старт;
- много готовых модулей, если когда-нибудь понадобится CMS;
- есть документация по ResultURL, SuccessURL, FailURL.

Минусы:

- нужно сравнить ставки и условия с ЮKassa;
- интерфейс и UX оплаты нужно проверить на практике.

## 3. CloudPayments / CloudKassir

Сильный вариант для аккуратного платежного UX и API-интеграции.

Подходит для:

- платежного виджета;
- API;
- возвратов;
- двухстадийных платежей;
- счетов по email;
- CloudKassir для онлайн-чеков.

Плюсы:

- хорошая API-документация;
- удобно делать встроенный платежный сценарий;
- есть связка с фискализацией.

Минусы:

- нужно отдельно проверять условия подключения и комиссии;
- для B2B-сценариев не заменяет счет/КП.

## 4. PayAnyWay

Можно рассматривать как альтернативный агрегатор.

Подходит для:

- карт;
- СБП;
- API;
- платежных ссылок;
- онлайн-касс по 54-ФЗ;
- B2B/B2C и некоторых нестандартных сценариев.

Плюсы:

- много платежных методов;
- заявлена интеграция с онлайн-кассами;
- есть API.

Минусы:

- нужно отдельно оценить качество поддержки, комиссии и удобство API.

## Предварительная Рекомендация По Оплате

Для Soliton:

1. **ЮKassa** - основной платежный провайдер.
2. **Robokassa** или **CloudPayments** - резервный/альтернативный провайдер.
3. **Оплата по счету** - обязательный отдельный сценарий для юрлиц.

В коде сразу делать абстракцию:

```ts
type PaymentProviderCode =
  | 'yookassa'
  | 'robokassa'
  | 'cloudpayments'
  | 'payanyway'
  | 'manual_invoice'

interface PaymentProvider {
  createPayment(order: Order): Promise<PaymentInitResult>
  handleWebhook(payload: unknown): Promise<PaymentWebhookResult>
  refund?(transactionId: string, amount: number): Promise<void>
}
```

## Агрегаторы И API Доставки

## 1. ApiShip

Рекомендуемый основной вариант как агрегатор доставки.

ApiShip позиционируется как интегратор служб доставки для e-commerce: один API, через который можно работать с разными службами.

Возможности:

- единый API;
- расчет стоимости доставки;
- список ПВЗ;
- создание заказов на доставку;
- получение этикеток;
- вызов курьера;
- трекинг;
- редактор тарифов;
- подключение разных служб доставки.

Важная особенность: ApiShip не замыкает договор на себя. По их документации, интернет-магазин работает по прямым договорам со службами доставки, а ApiShip стандартизирует обмен.

Плюсы:

- подходит для собственного сайта;
- можно подключить несколько служб через один слой;
- удобно для Codex и нашей архитектуры;
- снижает объем разработки по каждой службе отдельно.

Минусы:

- прямые договоры со службами доставки все равно могут понадобиться;
- нужно проверить список нужных служб и фактические тарифы;
- нужно протестировать ПВЗ, трекинг и создание отправлений.

## 2. Яндекс Доставка API

Подходит как отдельный канал доставки.

Возможности:

- API для передачи заказов;
- доставка сегодня / в течение дня;
- доставка по России;
- доставка до ПВЗ;
- курьерская доставка;
- получение токена в личном кабинете.

Плюсы:

- сильная инфраструктура;
- подходит для быстрой курьерской доставки;
- можно подключать к собственному сайту через API.

Минусы:

- для адресов могут потребоваться координаты/геокодирование;
- тестовая среда ограничена: в документации указано, что иногда интеграцию проверяют на реальных заказах, тестовый кабинет может выдаваться через менеджера;
- для B2B-грузов и транспортных компаний не заменяет СДЭК/Деловые Линии.

## 3. Shiptor / Shipitor API

Можно рассматривать как альтернативу или дополнительный вариант.

Возможности:

- API для создания отправлений/labels;
- управление отправками;
- доставка через партнерскую инфраструктуру;
- иногда используется как агрегатор/логистическая платформа.

Плюсы:

- есть API-документация;
- может закрывать часть e-commerce-логистики.

Минусы:

- нужно отдельно проверить актуальные условия, тарифы и покрытие под Soliton;
- для B2B-технических товаров может быть не первым выбором.

## 4. MetaShip

Еще один агрегатор доставки для интернет-магазинов.

Заявляет:

- единый API;
- личный кабинет;
- подключение разных служб доставки;
- СДЭК, Почта России, Dalli, Boxberry и другие службы;
- скидки на тарифы.

Плюсы:

- может быть полезен, если нужен договор через агрегатора и много служб в одном окне.

Минусы:

- нужно отдельно проверить API-документацию, условия договора и SLA;
- для code-first проекта я бы сначала тестировал ApiShip.

## 5. Прямые Интеграции Со Службами

Даже при агрегаторе нужно оставить возможность прямых интеграций:

- **СДЭК API** - ПВЗ, курьерка, расчет, отправления, трекинг.
- **Деловые Линии API** - B2B-грузы, терминалы, расчет, заявки.
- **Boxberry API** - ПВЗ и курьерка для B2C.
- **Почта России API** - широкое покрытие регионов.

Для Soliton прямые интеграции могут понадобиться, если:

- агрегатор не поддерживает нужный тариф;
- условия прямого договора выгоднее;
- нужен особый B2B-сценарий;
- нужно больше контроля над отгрузкой.

## Предварительная Рекомендация По Доставке

Для Soliton:

1. **ApiShip** - основной агрегатор доставки для MVP.
2. **СДЭК** - обязательно как ключевая служба, через ApiShip или напрямую.
3. **Деловые Линии** - для B2B-поставок и грузов, скорее прямой API.
4. **Яндекс Доставка** - как отдельный канал быстрой доставки.
5. **Boxberry / Почта России** - после проверки B2C-спроса.

В коде сразу делать абстракцию:

```ts
type ShippingProviderCode =
  | 'apiship'
  | 'cdek'
  | 'dellin'
  | 'yandex_delivery'
  | 'boxberry'
  | 'russian_post'
  | 'manual'

interface ShippingProvider {
  calculate(input: ShippingCalculationInput): Promise<ShippingRate[]>
  createShipment(order: Order): Promise<ShipmentResult>
  getStatus(trackingNumber: string): Promise<ShipmentStatus>
  getPickupPoints?(city: string): Promise<PickupPoint[]>
}
```

## Как Это Встроить В Наш Сайт

## Checkout Для Физлиц

1. Клиент выбирает товары.
2. Сайт рассчитывает доставку через ApiShip или конкретную службу.
3. Клиент выбирает ПВЗ/курьера.
4. Сайт создает заказ.
5. Сайт создает платеж через ЮKassa/Robokassa/CloudPayments.
6. После webhook оплаты заказ уходит в МойСклад.
7. После подтверждения менеджером создается отправление.
8. Клиент получает чек и трек-номер.

## Checkout Для Юрлиц

1. Клиент выбирает товары.
2. Нажимает "Запросить КП" или "Получить счет".
3. Заполняет реквизиты, ИНН, контакт, комментарий.
4. Сайт создает заявку в Payload.
5. Заявка уходит в МойСклад как заказ покупателя или лид/заказ в CRM.
6. Менеджер подтверждает цену, наличие и доставку.
7. Клиент получает счет/КП.
8. Доставка оформляется через Деловые Линии, СДЭК, ApiShip или вручную.

## Что Нужно Для Подключения

## Для Платежей

- юрлицо или ИП;
- расчетный счет;
- договор с платежным провайдером;
- данные для 54-ФЗ;
- онлайн-касса или облачное кассовое решение;
- ставки НДС и фискальные признаки в карточках товаров;
- публичные страницы оплаты, доставки, возврата;
- webhook endpoint на сайте;
- тестовый режим.

## Для Доставки

- договор с агрегатором или службами доставки;
- склад отгрузки;
- адрес склада;
- контакт отправителя;
- вес и габариты товаров;
- правила упаковки;
- договоренности по заборам/самопривозу;
- API-ключи;
- тестовые заказы;
- правила расчета доставки в checkout.

## Что Нужно Добавить В Карточки Товаров

Обязательно:

- вес;
- длина;
- ширина;
- высота;
- ставка НДС;
- единица измерения;
- название для чека;
- артикул;
- признак "доставка в ПВЗ доступна";
- признак "требует согласования доставки".

Желательно:

- вес в упаковке;
- габариты упаковки;
- кратность упаковки;
- страна происхождения;
- гарантия;
- срок поставки;
- склад/остаток.

## Архитектурный Вывод

Собственный сайт без inSales полностью реалистичен.

Нам не нужны модули inSales, если мы делаем собственную платформу. Вместо них подключаем напрямую:

- МойСклад API;
- ЮKassa / Robokassa / CloudPayments API;
- ApiShip / СДЭК / Деловые Линии / Яндекс Доставка API.

Это больше разработки на старте, но лучше подходит для:

- Codex;
- Git;
- SEO-архитектуры;
- B2B-заявок;
- RFQ;
- сложных карточек PDU;
- будущих кастомных интеграций.
